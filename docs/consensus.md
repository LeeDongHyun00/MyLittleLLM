# 독립 가설원의 합의: 예시를 통과하는 오답을 가려내기

작성일: 2026-11-18. [3차 교사 라운드](rule_round3.md)의 후속이다. 3차 라운드는 규칙 엔진을 키웠지만, 학생 모델과 합친 파이프라인의 남은 실패 대부분이 "보이는 예시는 통과하는 오답"이라 규칙을 늘려도 닿지 않았다. 이 문서는 그 병목을 겨냥한 개념과 측정이다. 모든 측정은 이 저장소 환경(CPU 4코어)에서 했다.

## 요약

1. **개념.** 학생 모델과 규칙 엔진은 틀리는 방식이 다르다. 모델은 과제를 잘못 읽고, 엔진은 예시를 우연히 맞힌다. 그래서 둘이 예시를 바꾼 새 입력들에서 같은 행동을 하면(확증) 그 답을 믿고, 확증되지 않은 답에만 모델 샘플을 더 받아 실행 결과의 합의로 고른다. 새 입력은 규칙(예시 변형 문법)이 만든다. 정답은 아무도 모른다.
2. **확증은 쓸 만한 신호다.** 1.5B 시험 분할에서 엔진이 확증한 답은 76개 중 64개(84%), 반박한 답은 29개 중 19개(66%) 맞았다. 0.5B는 79% 대 42%.
3. **1.5B 파이프라인: 시험 분할 98 → 102문제(64.9% → 67.5%).** 미리 고정한 규칙을 한 번 적용한 결과다. 엔진의 표를 뺀 대조군은 104문제였다. 검증 분할은 31 → 34문제. 과제당 모델 호출은 1.06 → 5.03회.
4. **게이트는 손해 없이 계산을 아꼈다.** 검증 분할의 모든 과제에 샘플을 받아도 34문제로 같았고 호출은 과제당 9.0회였다(게이트 6.0회).
5. **0.5B 학생에 그대로 옮겨도 효과가 났다.** 0.5B 파이프라인이 시험 분할 80 → 86문제(53.0% → 57.0%, 고침 7 / 깨뜨림 1)가 됐다(엔진 표를 뺀 대조군 85문제, 과제당 호출 1.09 → 5.85회).
6. **이론을 고쳤다.** 출처들의 일치는 확신의 근거가 되지만, 불일치는 누가 틀렸는지 알려 주지 않는다. 약한 출처(엔진)가 반대하면 대개 약한 출처가 틀린 것이다. 이득은 파이프라인이 이미 약하다고 아는 답(예시를 틀린 답, 엔진이 낸 답)을 바꾼 데서 났다. 선택 단계에서 엔진에게 준 표(λ)는 측정 가능한 이득이 없었다(1.5B −2, 0.5B +1, 검증 +1문제). 엔진은 투표자보다 "어디에 계산을 쓸지" 정하는 문지기로 쓸모가 있다.

## 1. 출발점: 예시를 통과하는 오답

[3차 라운드](rule_round3.md)에서 규칙 엔진은 강해졌지만 학생 모델과 합친 파이프라인은 거의 오르지 않았다. 남은 실패의 70% 이상이 "보이는 예시는 통과하지만 숨은 테스트에서 틀리는" 답이었기 때문이다(1.5B 시험 분할 53건 중 38건). 예시 하나로는 이런 답을 가려낼 수 없다. 약한 모델일수록 이런 거짓 양성을 더 많이 낸다는 보고도 있다(Stroebl 외).

이 저장소에는 오류의 원인이 서로 다른 두 가설원이 있다.

- **학생 모델**은 과제를 잘못 읽거나 알고리즘을 틀린다.
- **규칙 엔진**은 과제를 읽지 않는다. 예시를 재현하는 연산 조합을 찾을 뿐이라, 틀릴 때는 "예시와 우연히 맞은" 프로그램을 낸다.

두 출처가 틀리는 방식이 다르다는 점을 검증에 쓴다.

## 2. 이론: 독립 가설원의 합의

### 명제 1. 맞는 행동은 하나, 틀린 행동은 제각각이다

같은 과제에 대해 맞는 프로그램들은 모든 입력에서 같은 값을 낸다. 틀린 프로그램들은 저마다 다른 곳에서 틀린다(AlphaCode 논문의 표현으로는 "틀리는 방법은 많지만 맞는 해답은 같은 행동을 한다"). 그러므로 오류 원인이 다른 두 출처가 예시를 바꾼 새 입력들에서 같은 값을 내면, 둘이 같은 방식으로 틀렸을 가능성은 작다. 이 일치를 **확증**이라고 부른다.

간단한 모형으로 쓰면 이렇다. 모델의 답이 맞을 확률을 p, 엔진의 프로그램이 맞을 확률을 q, 두 오답이 탐침에서 우연히 같은 행동을 할 확률을 ε이라 하자. 두 출처의 오류가 독립이면

  P(맞음 | 확증) = pq / (pq + (1−p)(1−q)ε)

이고, ε이 작을수록 1에 가깝다. 실제로는 두 가지가 이 값을 깎는다. 하나는 **탐침이 오류가 드러나는 입력에 닿지 못하는 것**(사실상 ε가 커진다), 다른 하나는 **두 출처가 같은 방식으로 틀리는 것**(독립이 깨진다). 4절에서 둘을 따로 센다.

### 명제 2. 확증으로 계산을 가른다

확증된 답은 그대로 내고, 확증되지 않은 답에만 계산(모델 샘플)을 더 쓴다. 정답일 가능성이 낮은 곳에 계산이 몰린다. 대상은 세 종류다: 답이 예시를 틀린 과제, 답이 규칙 엔진에서 온 과제(엔진 단독 답의 정밀도는 낮다), 모델 답을 어떤 엔진 프로그램도 확증하지 못한 과제.

### 명제 3. 서로 다른 출처의 실행 기반 합의

확증되지 않은 과제에서는 후보(파이프라인 답, 규칙 없는 탐욕 답, 모델 샘플 8개, 엔진 프로그램 상위 10개) 가운데 예시를 통과하는 것만 남기고, 탐침에서의 행동으로 비교해 다음 점수가 가장 높은 것을 고른다.

  s(c) = (c와 같은 행동을 하는 모델 후보 수) / (모델 후보 수) + λ · [c가 엔진 프로그램이거나, 어떤 엔진 프로그램이 c와 같은 행동을 함]

앞 항은 실행 기반 최소 베이즈 위험(MBR-exec)이다. 뒤 항이 이 문서의 추가분으로, 규칙 엔진을 **기호적 사전분포**로 쓴다. 엔진은 같은 행동의 변형을 여러 개 내므로(근사 중복) 표를 개수로 세지 않고 "엔진 중 하나라도 같은 행동을 하는가"로 센다. 개수로 세면 같은 우연을 반복한 프로그램들이 큰 오답 묶음을 이룬다(CodeT 논문이 보고한 함정). λ = 0.5는 미리 정했다(엔진 전체의 표가 모델 표 총량의 절반).

### 탐침 문법: 입력을 만드는 규칙

탐침은 보이는 예시의 인자를 자료형을 지키며 바꾼 입력이다. 정답은 아무도 모른다. 탐침은 행동을 갈라 볼 뿐이다.

| 인자 | 변형 규칙 |
|---|---|
| 정수·실수 | 같은 부호의 가까운 값(±1, ±2, 2배, 절반 …) |
| 문자열 | 글자 바꾸기·지우기·겹치기·뒤집기, 단어 섞기·빼기·겹치기. 글자는 같은 부류(숫자는 숫자, 대문자는 대문자)로 바꾼다 |
| 리스트·튜플·집합 | 섞기·뒤집기·빼기·더하기·바꾸기·겹치기·정렬. 자료형은 유지한다 |
| 안쪽의 레코드·행 | 길이와 순서를 지키고 원소만 바꾼다 |
| 딕셔너리 | 값 바꾸기, 키 하나 빼기 |
| 인자 사이 관계 | 시퀀스의 길이였던 정수 인자는 바뀐 길이를 따라가고, 인덱스였던 정수는 범위 안으로 맞춘다 |

같은 예시에서는 늘 같은 탐침 24개가 나온다(결정적). 두 후보는 둘 다 값을 낸 탐침이 3개 이상이고 그중 값이 다른 것이 없으면 "같은 행동"이다. 한쪽만 예외를 낸 탐침은 무시한다. 탐침이 과제의 정의역 밖일 수 있고, 거기서는 맞는 프로그램도 예외를 낼 수 있기 때문이다.

규칙 엔진의 연산이 "답을 만드는 규칙"이었다면 탐침 문법은 "답을 시험할 입력을 만드는 규칙"이다. 두 가지 모두 모델 호출 없이 CPU에서 돈다.

새로운 점이라고 주장할 수 있는 것은 셋이다. (1) 합의에 참여하는 출처가 서로 다른 종류다: 모델의 샘플과, 교사가 규칙으로 증류한 열거기의 프로그램. (2) 계산을 확증으로 가른다: 열거기가 확증한 답에는 샘플을 쓰지 않는다. (3) 실행 입력을 모델이 아니라 규칙(예시 변형 문법)이 만든다. 각 요소의 선례는 위에 있고, 이 조합을 CPU의 작은 모델에서 잰 것이 이 문서의 기여다.

## 4. 측정 1: 확증은 얼마나 믿을 만한가 (저장된 답, 모델 호출 0회)

파이프라인의 최종 답이 예시를 통과한 모델 답인 과제마다, 그 답과 규칙 엔진의 상위 10개 프로그램을 같은 탐침 24개에서 실행했다. 엔진 프로그램 하나라도 같은 행동을 하면 "확증", 모든 엔진 프로그램과 값이 어긋나면 "반박"이다. 시험 분할은 개수만 셌다.

| 파이프라인 · 분할 | 예시를 통과한 모델 답 | 엔진이 확증 | 엔진이 반박 | 엔진 프로그램 없음 |
|---|---|---|---|---|
| 1.5B · 학습 (교사가 봄) | 145개 중 129개 (89%) | 134개 중 124개 (93%) | 8개 중 2개 (25%) | 3개 중 3개 (100%) |
| 1.5B · 검증 | 35개 중 27개 (77%) | 17개 중 15개 (88%) | 7개 중 3개 (43%) | 11개 중 9개 (82%) |
| 1.5B · 시험 | 119개 중 92개 (77%) | 76개 중 64개 (84%) | 29개 중 19개 (66%) | 14개 중 9개 (64%) |
| 0.5B · 시험 | 90개 중 61개 (68%) | 61개 중 48개 (79%) | 19개 중 8개 (42%) | 10개 중 5개 (50%) |

- 확증된 답은 반박된 답보다 확실히 자주 맞는다. 1.5B 시험 분할에서 84% 대 66%, 0.5B에서 79% 대 42%다.
- 확증된 답도 틀릴 수 있다. 모든 샘플이 일치해도 MBPP 오류가 19% 남는다는 보고(Valentin 외)와 같은 크기다.

개발 분할에서 확증됐지만 틀린 답은 12개였다. 그중 10개는 참조 답안과도 모든 탐침에서 같은 값을 냈다. 탐침 문법이 만들지 않는 입력에서만 틀린 것이다(빈 입력에서 예외, 아주 큰 입력에서 시간 초과, 참조 답안의 자료형 관례). 모델과 엔진이 보통 입력에서 같은 방식으로 틀린 것은 2개뿐이다. 즉 확증의 한계는 출처 간 오류 상관보다 탐침의 범위에서 왔다.

그래서 경계 입력(빈 값, 원소 하나, 0)을 먼저 넣고, 경계 입력에서 한쪽만 예외를 내면 불일치로 보는 탐침도 시험했다. 학습 분할에서 확증된 답의 정밀도가 124/134 → 112/119로 올랐지만 검증 분할에서는 15/17 → 14/17로 나아지지 않아, 미리 고정한 실험에는 첫 문법을 그대로 썼다.

## 5. 측정 2: 확증 게이트 + 합의 선택

규칙과 모든 수치는 샘플을 받기 전에 `reports/rule_pilot/consensus_protocol.json`에 고정했다: 샘플 k = 8, 온도 0.8, 시드 1000~1007, 규칙 없는 프롬프트, λ = 0.5, 탐침 24개, 일치 기준 3개. 관문은 "검증 분할에서 3차 파이프라인(31/45)보다 적게 풀지 않는다"였고, 통과한 뒤 시험 분할을 한 번 평가했다. λ = 0(엔진 표 없음)은 미리 정한 대조군이다.

| | 검증 45 (관문) | 시험 151 (1회) | 시험: 3차 대비 고침 / 깨뜨림 | 과제당 모델 호출 (시험) |
|---|---|---|---|---|
| 1.5B 단독(규칙 없음) | 24 (53.3%) | 89 (58.9%) | — | 1.00 |
| 3차 파이프라인(분기-선택 + 규칙 엔진) | 31 (68.9%) | 98 (64.9%) | — | 1.06 |
| **+ 확증 게이트 합의 (λ = 0.5)** | **34 (75.6%)** | **102 (67.5%)** | 6 / 2 (p=0.289) | 5.03 |
| + 합의, 엔진 표 없음 (λ = 0) | 33 (73.3%) | 104 (68.9%) | 7 / 1 (p=0.070) | 5.03 |

- 시험 분할에서 1.5B 파이프라인이 98 → 102문제가 됐다(95% 신뢰구간 59.7–74.5%). 3차 파이프라인 대비 고침 6, 깨뜨림 2, 정확 맥니마 검정 p=0.289.
- 엔진의 표를 뺀 대조군(λ = 0, 순수한 실행 기반 합의)은 104문제였다(고침 7, 깨뜨림 1). 엔진을 투표자로 넣은 것이 이 분할에서는 오히려 2문제 손해였다.
- 비용: 과제당 평균 모델 호출이 1.06회에서 5.03회로 늘었다. 확증된 과제에는 샘플을 쓰지 않았다.

어디서 이득이 났는지 대상 종류별로 나누면 그림이 분명해진다(답이 바뀐 과제만, 바뀌기 전 → 후의 해결 수).

| 대상 종류 | 검증, λ = 0.5 | 검증, λ = 0 | 시험, λ = 0.5 | 시험, λ = 0 |
|---|---|---|---|---|
| 답이 예시를 틀림 | 2개: 0 → 1 | 2개: 0 → 1 | 8개: 0 → 3 | 8개: 0 → 3 |
| 답이 규칙 엔진에서 옴 | 1개: 0 → 1 | 1개: 0 → 1 | 5개: 0 → 2 | 8개: 1 → 3 |
| 모델 답, 엔진이 확증 못 함 | 2개: 0 → 1 | 1개: 0 → 0 | 10개: 4 → 3 | 8개: 2 → 3 |

- **답이 예시를 틀렸거나 규칙 엔진에서 온 과제**에서는 두 분할 모두 꾸준히 올랐다. 파이프라인이 이미 약하다고 알고 있던 답이다.
- **모델 답이 예시는 통과하는데 엔진이 확증하지 못한 과제**에서는 바꿔도 얻은 것이 없다(시험 분할 λ = 0.5에서 4 → 3). 이 경우 엔진이 반대한 것은 대개 엔진이 틀렸기 때문이다. 3차 라운드에서 센 대로, 둘 다 예시를 통과할 때 모델만 맞은 과제가 엔진만 맞은 과제보다 8배 많았다(24 대 3).

여기서 이론을 고쳐야 한다. **독립 출처의 일치는 확신의 근거가 되지만, 불일치는 누가 틀렸는지 알려 주지 않는다.** 약한 출처가 반대하면 대개 약한 출처가 틀린 것이다. 그래서 규칙 엔진은 선택의 투표자보다 "어디에 계산을 쓸지" 정하는 문지기로 더 쓸모가 있었다. 명제 3의 엔진 표(λ)는 두 학생을 합쳐도 측정 가능한 이득이 없었다(1.5B 시험 −2, 0.5B 시험 +1, 1.5B 검증 +1문제).

## 6. 비용 곡선과 게이트의 값

대상 과제의 샘플을 앞에서부터 k개만 쓰면 비용과 정확도가 어떻게 바뀌는지 검증 분할에서 쟀다(미리 정한 본 실험은 k = 8).

| 대상 과제당 샘플 수 | 0 | 2 | 4 | 8 |
|---|---|---|---|---|
| 검증 분할 해결 (45) | 31 | 33 | 33 | 34 |
| 과제당 평균 모델 호출 | 1.00 | 2.24 | 3.49 | 5.98 |

샘플 2개(과제당 평균 호출 약 2.2회)에서 이득의 대부분이 난다. 샘플 0개, 즉 저장된 답과 엔진 프로그램만으로 고르면 아무것도 바뀌지 않았다. 합의에는 새 샘플이 필요하다.

검증 분할의 모든 과제에 샘플을 받은 대조군(게이트 없음)은 34문제, 과제당 호출 9.00회였다. 확증 게이트를 쓴 본 규칙은 34문제, 5.98회다.

## 7. 다른 학생으로 옮기기: 0.5B

같은 규칙을 그대로(같은 k, 온도, 시드, λ, 탐침) 0.5B 학생의 3차 파이프라인에 적용했다. 샘플도 0.5B 모델이 냈다. 미리 정한 대로 시험 분할에서 한 번 평가했다.

| 0.5B, 시험 151 | 해결 | 3차 대비 고침 / 깨뜨림 | 과제당 모델 호출 |
|---|---|---|---|
| 0.5B 단독 | 56 (37.1%) | — | 1.00 |
| 3차 파이프라인 | 80 (53.0%) | — | 1.09 |
| **+ 확증 게이트 합의 (λ = 0.5)** | **86 (57.0%)** | 7 / 1 (p=0.070) | 5.85 |
| + 합의, 엔진 표 없음 (λ = 0) | 85 (56.3%) | — | 5.85 |

0.5B에서도 3차 파이프라인 위에 6문제가 더 풀렸다(고침 7, 깨뜨림 1). 0.5B는 대상 과제가 90개로 1.5B(75개)보다 많았는데, 규칙 엔진이 낸 답이 42개로 많았기 때문이다. 약한 학생일수록 엔진에 기대는 과제가 많고, 그 답을 샘플 합의로 다시 볼 여지도 크다.

## 8. 한계

- **계산이 늘어난다.** 대상 과제마다 샘플 8개를 받으므로 과제당 평균 모델 호출이 1회에서 약 5~6회로 는다. 같은 CPU에서 1.5B 모델로 과제당 수십 초가 더 든다. 샘플 2개만 써도 이득의 대부분이 났지만(검증 분할), 그 곡선은 작은 표본에서 잰 것이다.
- **확증은 보증이 아니다.** 확증된 답도 시험 분할에서 16%가 틀렸다. 개발 분할에서 그 대부분은 탐침이 닿지 않는 입력(빈 입력, 아주 큰 입력, 참조 답안의 자료형 관례)에서 틀렸다. 경계 입력을 넣은 탐침은 학습 분할에서 정밀도를 올렸지만 검증 분할에서는 그대로여서 채택하지 않았다.
- **표본이 작다.** 검증 분할은 45문제, 시험 분할은 151문제다. 시험 분할은 앞선 라운드들에서도 평가에 썼다(내용은 보지 않고 개수만).
- **규칙은 미리 고정했지만 설계는 이 저장소의 경험에서 나왔다.** λ, k, 온도, 탐침 수는 어느 분할에서도 조정하지 않았다. 다만 "확증"이라는 아이디어 자체는 앞선 라운드의 시험 분할 분석(병목의 위치)을 보고 떠올린 것이다.
- **학생 모델 두 개, 벤치마크 둘.** Qwen2.5-Coder 0.5B·1.5B로 MBPP+를 쟀고, 1.5B로 HumanEval+를 한 번 쟀다(아래 '처음 보는 벤치마크').
- **탐침의 정답은 모른다.** 합의는 다수의 행동을 고를 뿐이다. 모델 샘플 대부분이 같은 방식으로 틀리면 합의도 틀린다.

### 처음 보는 벤치마크: HumanEval+

규칙·연산·문구·임계값을 쓰는 동안 한 번도 보지 않은 HumanEval+(164문제)에서, 결과를 보기 전에 적은 문서(`reports/rule_pilot/humaneval_protocol.json`)대로 한 번만 돌렸다. 절차와 수치(k = 8, 온도 0.8, 시드, λ)는 MBPP+와 같다. 확증되지 않아 표본을 받은 과제는 164개 중 83개였다.

| 시스템(1.5B) | 푼 문제 | 학생 혼자 대비 고침 / 깨뜨림 |
|---|---|---|
| 학생 혼자 | 109 (66.5%) | — |
| 분기-선택 파이프라인 | 110 (67.1%) | 1 / 0 |
| 합의, λ = 0.5(주 설정) | 113 (68.9%) | 6 / 2, p = 0.29 |
| 합의, λ = 0 | 115 (70.1%) | 6 / 0, p = 0.03 |

합의는 처음 보는 벤치마크에서도 학생 혼자보다 나았고, 엔진의 표를 뺀 λ = 0이 다시 더 좋았다. 규칙 엔진 혼자는 22문제(13.4%)라 HumanEval+에서는 라이브러리가 닿는 과제 자체가 적다. 그래서 여기서의 이득은 거의 모두 모델 표본의 합의에서 났다.

## 9. 다음 단계

1. **샘플을 약한 답에만 쓴다.** 이득은 "답이 예시를 틀렸거나 엔진에서 온" 과제에서 났고, 예시를 통과한 모델 답을 바꾼 것은 본전이었다. 그 두 종류에만 샘플을 쓰면 시험 분할 기준 대상이 75개에서 32개로 줄어 호출이 과제당 약 2.7회가 된다. 이 규칙은 결과를 본 뒤 떠올린 것이라 다음 실험에서 따로 검증해야 한다.
2. **엔진의 표는 신뢰도에 맞춰 단다.** 독립 투표자의 최적 가중치는 log(p/(1−p))에 비례한다(Nitzan–Paroush의 고전적 결과). 예시를 우연히 맞히기 쉬운 엔진은 모델보다 작은 가중치를 받아야 하고, 개발 분할에서 p를 따로 추정해 정할 수 있다.
3. **탐침의 범위를 넓힌다.** 확증됐지만 틀린 답은 대부분 빈 입력, 아주 큰 입력, 자료형 관례처럼 탐침이 닿지 않는 곳에서 틀렸다. 경계 입력을 넣되, 정의역 밖 입력에서 생기는 잡음을 줄이는 규칙(예: 엔진이 값을 내는 경계 입력만 쓰기)이 필요하다.
4. **더 큰 학생.** 같은 구조를 3B 학생에 얹으면 샘플의 질이 올라 합의가 더 잘 들을 것으로 예상한다. CPU에서 샘플당 시간이 약 2배라 계산 예산과 함께 재야 한다.
