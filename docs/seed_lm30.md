# SeedLM-30~31: 뼈대는 되풀이되고, 구멍만 채우면 닿는다

작성일: 2026-11-22. [보강 설계](seedlm_design_next.md) 11절의 첫 단계다. 교사(Opus 5.5)에게 무엇을 주입할지 정하기 전에, 지금 가진 교사 프로그램만으로 처음 보는 프로그램이 어디까지 표현되는지 재고(SeedLM-30), 그 구조를 강제한 탐색이 실제로 얼마나 닿는지 쟀다(SeedLM-31). 교사 토큰은 쓰지 않았다.

## 요약

- 프로그램에서 5토큰 이하의 부분 트리를 모두 구멍으로 바꾼 **뼈대**는 되풀이된다. 학습 프로그램에서 두 번 이상 나온 뼈대 약 220개로 보류 교사 과제 139개 중 118개, 엔진이 못 푸는 개발 과제의 한 줄 식 15개 중 9개가 표현된다(SeedLM-30).
- 뼈대의 고정 토큰은 강제하고 구멍만 코더가 채우는 탐색을 붙이자, 맞는 후보가 하나라도 있는 과제가 교사 보류 과제에서 67 → **88**개, 엔진이 못 푸는 개발 과제 28개 중 3 → **11**개로 늘었다(SeedLM-31). 등록 기준(100)에는 못 미쳐 판단 보류다.
- 대가는 후보 수다. 과제당 예시를 맞히는 후보가 3개에서 70개 안팎으로 늘었다. 이제 남은 문제는 거의 고르기다.

## 1. 뼈대의 덮임 (SeedLM-30)

`scripts/seedlm30_sketches.py`, `reports/seedlm/sketch_coverage.json`. 측정 전 등록 없는 탐색 진단이고, 설정은 학습 데이터의 5겹 교차 검증으로 골랐다.

| 교사가 쓴 학습 프로그램 3,143개, 다른 네 몫에서 2번 이상 나온 뼈대 | 덮인 프로그램 |
|---|---|
| 구멍 1토큰 (리프만) | 2% |
| 구멍 3토큰 이하 | 38% |
| **구멍 5토큰 이하** | **62%** (뼈대 약 220개, 구멍 중앙값 3개) |
| 같은 설정, 가장 흔한 뼈대 50개만 | 52% |
| 같은 설정, 학습 프로그램 500 / 1,000 / 2,000개로 만든 뼈대 | 48% / 55% / 60% |

| 보류 집합 (구멍 5토큰 이하, 2번 이상) | 뼈대 + 구멍으로 표현됨 |
|---|---|
| 교사 보류 139 | 118 (그중 65개는 프로그램 전체가 5토큰 이하) |
| ― 새 조합이 낀 77 | 61 |
| ― 저장된 코더 48개 누구도 못 맞힌 32 | 18 |
| 범위 밖(엔진이 못 푸는 개발 과제의 한 줄 식) 15 | 9 |

처음 보는 프로그램도 큰 구조는 이미 본 것이고, 새로운 것은 구멍 속의 작은 식이다. 코더가 "본 조합만 쓴다"는 것은 토큰 사이의 연결 이야기였다. 뼈대 단위에서는 본 구조가 대부분을 차지한다. 교사 프로그램을 두 배로 늘려도 덮임은 5~6%p만 늘어, 교사가 풀이를 더 쓰는 것은 효율이 낮다.

## 2. 뼈대를 강제한 탐색 (SeedLM-31)

`mylittlellm/seedlm/sketch.py`, `scripts/seedlm31_sketch_search.py`, `reports/seedlm/seedlm31_protocol.json`(측정 전 등록).

- **뼈대 목록:** 학습 프로그램에서 두 번 이상 나온 뼈대(한 구멍짜리 전체 뼈대는 뺌).
- **순위기:** 설명의 내용어, 인자 수, 보이는 출력의 종류로 뼈대를 매기는 나이브 베이즈. 학습 데이터 교차 검증에서 프로그램의 실제 뼈대를 상위 8개 안에 76%, 32개 안에 92%, 64개 안에 97% 넣었다.
- **탐색:** 과제마다 상위 64개 뼈대를 전위 코더 s20-p5로 푼다. 고정 토큰은 강제하고, 구멍마다 5토큰 이하의 부분 트리를 코더가 채운다. 뼈대마다 가설 6개, 뼈대 16개씩 한 배치로 돌린다. 코더는 처음 보는 부모 → 자식 연결에 확률을 거의 주지 않으므로(SeedLM-5), 그 연결을 강제로 깔아 주고 코더가 잘하는 작은 부분만 맡기는 것이다.

| 맞는 후보가 하나라도 있는 과제 | 코더 자신의 빔 (폭 32) | 뼈대 탐색 | 둘 다 | 뼈대 탐색으로만 |
|---|---|---|---|---|
| 교사 보류 139 | 67 | 78 | **88** | 21 |
| 개발 과제 93 | 57 | 46 | **67** | 10 |
| ― 그중 엔진이 못 푸는 28 | 3 | | **11** | |

| 비용 | 코더 자신의 빔 | 뼈대 탐색 |
|---|---|---|
| 과제당 시간 (CPU 4코어) | 0.9초 | 4.6초 |
| 과제당 예시를 맞히는 후보 (교사 / 개발) | 3.3 / 2.3 | 71.1 / 50.6 |

주 측정은 교사 보류 과제에서 100개 이상이면 지지, 80개(지금까지 코더 하나의 빔이 닿은 최고)를 넘지 못하면 기각으로 정했다. 88개라 판단 보류다. 보류 과제 중 실제 뼈대가 목록에 있는 53개 가운데 52개가 상위 64개 안에 들었으니 순위기는 거의 놓치지 않았다. 모자란 것은 구멍 채우기다. 옳은 뼈대를 줘도 코더가 구멍을 다 맞게 채우는 것은 일부다.

가장 눈에 띄는 것은 실제 과제다. 엔진이 못 푸는 개발 과제에서 맞는 프로그램이 손에 들어온 과제가 3개에서 11개가 됐다. 지금까지 시스템이 막혀 있던 "도달" 틈(엔진 너머)을 처음으로 크게 연 결과다. 그러나 맞는 것 하나가 틀린 후보 수십 개 사이에 섞여 있다. 시스템 점수로 바꾸려면 고르기가 필요하다.

## 3. 다음

설계 11.3의 b단계다. 후보 70개 안팎에서 고르는 규칙을 교사 보류 과제에서 찾고, 개발 과제에서 확인하도록 등록한다. 후보로는 코더들의 합의(다른 코더들이 같은 행동의 프로그램을 쓰는가), 다른 코더의 확률, 뼈대의 순위 점수, 프로그램 길이, 엔진의 확신을 쓴다. 지금까지 순위를 바꾼 것이 독립적인 코더들의 합의뿐이었으므로 그것이 중심이다. 엔진을 깨뜨리지 않도록, 뼈대 후보는 엔진이 답을 못 내거나 확신하지 않는 과제에만 쓰는 안부터 본다.
