# SeedLM-2: 설명을 읽는, 처음부터 만든 모델

작성일: 2026-11-19. [SeedLM](seed_lm.md)의 후속이다. 사전학습 가중치 없이 처음부터 학습한다는 원칙은 그대로이고, 측정은 모두 이 저장소 환경(CPU 4코어)에서 했다.

## 요약

- 602만 파라미터 트랜스포머를 CPU에서 60분 학습했다. 과제 설명의 **단어**를 읽고, 보이는 예시 하나를 함께 보고, 규칙 라이브러리 연산 780개와 설명 속 상수로 프로그램을 쓴다. 제안은 실행으로 검증한다.
- 언어는 벤치마크가 아니라 교사에게서 왔다. 교사 서브에이전트가 연산마다 쓴 문구 2,340개로 합성 프로그램의 설명을 지었다.
- 잠근 시험 분할(MBPP+ 151문제, 한 번만 평가): SeedLM-2 혼자 **58문제(38.4%)**. SeedLM-1은 43문제, 사전학습된 Qwen2.5-Coder-0.5B 혼자는 56문제다.
- 규칙 엔진과 합치면 엔진 혼자 68 → **70문제(46.4%)**. 모델은 엔진의 최고 점수 후보들이 동점일 때만 고른다. 학생 모델과 합친 파이프라인은 1.5B 98 → 98, 0.5B 80 → 81로 거의 움직이지 않았다.
- HumanEval+(164문제, 이 저장소에서 아무것도 맞추지 않은 벤치마크, 한 번만 평가): 엔진 혼자 22 → 동점 처리 23문제, 1.5B 파이프라인 110 → 110. SeedLM-2 혼자는 17문제(10.4%)다. MBPP와 문제 모양이 달라 라이브러리가 닿는 과제 자체가 적다.
- 실패의 원인을 갈랐다. 설명을 완벽하게 읽어도 고칠 수 있는 엔진 실패는 많아야 30%이고(실제로는 더 적다), 나머지는 라이브러리 연산을 두세 개 이어서는 표현되지 않는다. 그리고 모델이 실제 과제에서 놓치는 경우의 대부분은 정답 연산을 아예 떠올리지 못한 경우다(아래 7절).

## 1. 무엇을 키웠나

SeedLM-1은 과제 설명을 읽지 못했다. 설명은 "키워드 표가 찾아낸 연산 목록"으로만 들어갔다. 이 표는 거칠다. 예를 들어 "find"라는 단어가 `index` 연산을 부르기 때문에, "n개의 가장 작은 수의 합을 구하라"는 과제에서 엔진은 `a0.index(a1)`이라는 우연한 프로그램을 첫째로 고른다(예시 [5, 1, 4, 2], 2 → 3에서 2의 위치가 마침 3이다).

| | SeedLM-1 | SeedLM-2 |
|---|---|---|
| 설명 | 키워드 표가 찾은 연산 토큰 | **설명의 단어**(어휘 1,482개) + 키워드 표의 연산 토큰(학습 때 절반은 지운다) |
| 연산 | 328개 | **780개**(3차 라운드까지의 라이브러리 전체) |
| 상수 | 없음 | 설명에 적힌 수·문자열(c0~c5)을 프로그램에 쓸 수 있다 |
| 참·거짓 결과 | 학습에서 제외 | 포함(실제 과제의 3분의 1이 판정 과제) |
| 학습 데이터 | 합성 프로그램 | 합성 프로그램 + **교사가 쓴 문구로 지은 설명** + 실제 개발 과제 |
| 크기 | 142만 파라미터, 폭 160, 4층 | 602만 파라미터, 폭 256, 6층 |
| 수치 형식 | float32 | bfloat16 혼합(이 CPU의 AMX에서 약 15% 빠름) |

구조는 SeedLM-1과 같다: RoPE, RMSNorm, 코사인 어텐션, ReLU², 직교 초기화, 잔차 투영 0 초기화, 은닉 행렬은 Muon, 나머지는 AdamW. 한 시퀀스는 `설명 단어 | 상수 | 예시 입력 바이트 | 예시 출력 바이트 | 키워드 표의 연산 | 프로그램`이고 프로그램 부분만 학습한다. 추론은 문법으로 제한한 빔 탐색(폭 32)이고, 예시를 재현하는 프로그램만 남긴다.

## 2. 언어는 교사에게서 증류했다

합성 프로그램에는 설명이 없다. 그래서 교사 서브에이전트 다섯이 연산 780개마다 "그 연산이 하는 일을 짧은 과제 설명처럼 쓴 문구"를 세 개씩 썼다(`data/seedlm/operator_phrases.json`, 2,340개). 합성 프로그램의 설명은 이 문구들을 이어 붙여 만든다: 안쪽 연산부터 "and then"으로 잇거나, 바깥 연산을 앞세워 "of"로 잇는다. 단어를 조금 빼고 넣는 잡음도 섞는다. 벤치마크의 문장을 쓰지 않고 교사의 언어 지식을 학생에게 옮기는 방법이다.

실제 과제도 섞었다. 학습 분할과 추가 풀(MBPP+ 밖의 MBPP 과제) 가운데 정답 프로그램을 아는 525개다. 대부분은 엔진의 첫 프로그램이 정답인 과제이고, 35개는 엔진이 순위나 키워드 관문 때문에 놓쳤지만 오라클이 찾아낸 과제다. 추가 풀의 5분의 1은 평가용으로 뺐다(정답 프로그램을 아는 75개, 과제 테스트로 채점하는 94개). 검증·시험 분할은 쓰지 않았다.

두 번째 교사 작업으로, 무작위 합성 프로그램 1,250개에 교사가 자연스러운 과제 설명을 붙였다(`data/seedlm/natural_descriptions.json`). 문구를 이어 붙인 설명과 실제 과제 문장 사이의 거리를 재기 위해서다(4절).

## 3. 학습된 독자가 어디까지 도울 수 있나: 오라클 진단

엔진이 못 푸는 개발 과제 154개에서, 예시와 일치하는 프로그램을 3,000개까지 모아 과제의 테스트로 정답을 찾았다(`scripts/seedlm2_ceiling.py`).

| 원인 | 과제 수 | 학습된 독자가 고칠 수 있나 |
|---|---|---|
| 순위: 정답 프로그램이 있는데 첫째가 아님 | 22 | 예 |
| 관문: 키워드 관문을 모두 열어야 정답이 나옴 | 24 | 예 |
| 범위 밖: 라이브러리 연산을 이어서는 정답이 없음 | 103 | 아니오 |
| 예시를 읽을 수 없음 | 5 | — |

설명을 완벽하게 읽는 모델이 있어도 엔진 실패의 30%까지만 고칠 수 있다. 실제 상한은 이보다 낮다. 추가 풀 과제의 테스트는 세 개뿐이라, "정답"으로 잡힌 프로그램 중 상당수가 우연이다. 예를 들어 "튜플 안에 리스트가 몇 개 있나"의 정답으로 잡힌 프로그램은 `txt_lcs_length(sorted(a0), a0)`이다. 순위·관문 46건 중 설명과 뜻이 맞는 프로그램은 대략 절반이다.

## 4. 학습: 합성에서는 잘 읽지만 실제 과제로 갈수록 떨어진다

| 실행 | 학습 데이터 | 학습 | 합성 보류 | 교사 자연어 보류 | 실제 과제 보류 |
|---|---|---|---|---|---|
| s2-main | 합성 30만 + 실제 524(×64) | 60분, 4,461걸음 | 83.3% | — | 45.9% |
| s2-nat | 합성 30만(깨끗한 것만) + 실제 525(×30) + 교사 자연어 1,125(×40) | 70분, 5,922걸음 | 87.0% | 70.4% | 41.3% |

수치는 첫째 후보가 예시를 재현하는 비율이다(합성 300개, 교사 자연어 125개, 실제 74~75개). 폭 8의 빔 안에 재현하는 후보가 있는 비율은 합성 98.7~99.3%, 실제 68~76%였다.

**증류 격차.** 같은 모델이 교사가 지은 설명에서 83~87%, 교사가 자연스럽게 쓴 설명에서 70%, 실제 과제 설명에서 41~46%를 맞힌다. 교사의 자연어를 학습에 섞자 자연어 보류 성적은 올랐지만 실제 과제 성적은 오히려 내려갔다(45.9 → 41.3%, 보류 75개라 차이는 오차 안). 문장을 자연스럽게 만드는 것만으로는 격차가 닫히지 않는다. 실제 과제와의 차이는 문체가 아니라 **무엇을 묻는가**(어떤 프로그램이 실제로 쓰이는가)에 있다는 해석과 맞는다.

## 5. 실제 과제에서: 약한 독자는 강한 쪽이 약한 곳에서만 행동해야 한다

방법마다 과제당 프로그램을 하나만 내고, 보이는 예시로 검증한다(`scripts/seedlm2_tasks.py`).

- `engine`: 출하한 규칙 엔진(키워드 관문, 손으로 정한 순위)
- `model`: SeedLM-2의 빔에서 예시를 재현하는 첫 후보
- `rerank`: 엔진 후보 40개 + 모델 후보를 모델의 로그확률로 다시 정렬
- `open`: rerank와 같되, 모델 빔에 나온 연산은 키워드 관문을 연다
- `gate`: 모델은 관문만 열고 순위는 엔진이 정한다
- `tie`: 엔진의 최고 점수 후보가 여럿 동점일 때만 모델이 고른다
- `fill`: 엔진이 아무 프로그램도 못 낼 때만 모델이 답한다

추가 풀의 보류 과제 94개(과제 테스트 세 개로 채점):

| | engine | model | rerank | open | gate | tie | fill |
|---|---|---|---|---|---|---|---|
| s2-main | 65 | 49 | 60 | 60 | 61 | **67** | 65 |
| s2-nat | 65 | 53 | 65 | 64 | 59 | **67** | 65 |

엔진이 푼 65문제에서 rerank는 7문제를 잃고 2문제를 얻었다. 모델의 읽기는 엔진의 손 순위보다 덜 믿을 만하다. 그래서 모델이 엔진이 확신하지 못하는 곳(동점)에서만 행동하게 하자 잃는 것 없이 2문제를 얻었다. 엔진이 아무것도 못 낸 14문제에서 모델이 푼 것은 0이었다(`fill`이 `engine`과 같다).

엔진 점수와 모델 로그확률을 특징으로 로지스틱 순위기를 학습해 보기도 했다(`scripts/seedlm2_stack.py`). 보류 93문제에서 66(엔진 65, 후보 안 오라클 72)으로, 동점 처리와 비슷했다.

`gate`, `tie`, `fill`은 보류 결과를 본 뒤에 추가했다. 그래서 보류 성적으로 고른 것은 깨끗한 선택이 아니고, 그 사실을 사전 등록 문서의 부록에 적었다(`reports/seedlm/seedlm2_protocol.json`). 검증 관문과 시험·HumanEval+ 평가 규칙은 바꾸지 않았다. 체크포인트는 규칙대로 보류 성적이 같으면 먼저 학습한 s2-main을 썼다.

## 6. 사전 등록한 관문과 시험

**검증 관문**(45문제, 1.5B 분기-선택 파이프라인에서 엔진 자리에 `tie`): 31 → 31, 엔진보다 적지 않다는 조건을 넘었다. 이득도 없었다. 엔진 혼자는 19, `tie` 혼자도 19였다.

**잠근 시험 분할**(151문제, 한 번만):

| | 엔진 | SeedLM-2 혼자(`model`) | rerank | open | gate | **tie(사전 선택)** | fill |
|---|---|---|---|---|---|---|---|
| 모델 없이 | 68 | 58 | 65 | 66 | 65 | **70** | 68 |
| 1.5B 파이프라인 | 98 | 98 | 98 | 98 | 98 | **98** | 98 |
| 0.5B 파이프라인 | 80 | 78 | 80 | 80 | 80 | **81** | 80 |

비교 기준(같은 시험 분할): Qwen2.5-Coder-0.5B 혼자 56, 1.5B 혼자 89, SeedLM-1 혼자 43.

- 사전학습 없이 CPU 1시간 학습한 600만 파라미터 모델이, 교사가 쓴 라이브러리를 조합해 4비트 0.5B 코더와 비슷한 수의 과제를 푼다(58 대 56). 엔진과 합친 "처음부터 만든 시스템"은 70으로 0.5B보다 14문제 많고 1.5B보다 19문제 적다.
- 학생 모델과 합친 파이프라인은 거의 움직이지 않는다. 파이프라인은 학생의 답이 보이는 예시를 통과하지 못할 때만 엔진을 부르는데, 남은 실패의 70% 이상은 예시를 통과하는 오답이다([합의 문서](consensus.md)).

## 7. HumanEval+

사전 등록 문서(`reports/rule_pilot/humaneval_protocol.json`)대로 한 번만 돌렸다. 학생은 1.5B, 보이는 예시는 docstring의 첫 호출 예다(164문제 중 121문제에 있다). 등록 문서는 SeedLM-2를 "재정렬"로 적었지만, SeedLM-2 자신의 규칙(5·6절)이 고른 방법은 동점 처리라서 그것을 썼다.

| 시스템 | 푼 문제 | 비율 | 학생 혼자 대비 고침 / 깨뜨림 |
|---|---|---|---|
| 학생 혼자(1.5B) | 109 | 66.5% | — |
| 분기-선택 파이프라인 | 110 | 67.1% | 1 / 0 |
| SeedLM-2 동점 처리를 넣은 파이프라인 | 110 | 67.1% | 1 / 0 |
| 규칙 엔진 혼자 | 22 | 13.4% | — |
| 엔진 + SeedLM-2 동점 처리 | 23 | 14.0% | — |
| SeedLM-2 혼자 | 17 | 10.4% | — |
| 합의(λ = 0.5, 등록한 주 설정) | 113 | 68.9% | 6 / 2 (p = 0.29) |
| 합의(λ = 0, 함께 보고하기로 한 설정) | 115 | 70.1% | 6 / 0 (p = 0.03) |

- 규칙 엔진과 SeedLM-2는 HumanEval+에서 거의 쓸모가 없다. 라이브러리 연산은 MBPP 과제에서 나왔고, HumanEval의 과제는 더 길고 조건이 많다. 엔진 혼자 13.4%로 MBPP+ 시험 분할(45.0%)의 3분의 1이다.
- 합의 단계는 처음 보는 벤치마크에서도 통했다. 확증되지 않은 답에만 표본을 받는 방식으로 학생 혼자보다 4~6문제 많고, 모델 호출은 과제당 약 4회 늘었다. MBPP+ 시험 분할에서처럼 엔진의 표를 뺀 λ = 0이 더 좋았다(115 대 113). 선택에서 엔진에게 표를 주는 설계는 두 벤치마크 모두에서 이득이 없었다.

## 8. 모델이 실제 과제에서 무엇을 놓치나

정답 프로그램을 아는 실제 보류 과제 75개에서 빔(폭 16)을 들여다봤다.

| | 과제 수 |
|---|---|
| 예시를 재현하는 첫 후보가 정답 | 44 |
| 정답이 빔 안에 있지만 더 뒤에 | 4 |
| 정답이 빔에 없음 | 27 |

놓친 27개 중 상당수는 설명이 개념을 정확히 부르는데도 정답 연산이 빔에 없다. "두 문자열을 모두 부분열로 갖는 가장 짧은 문자열의 길이"(정답 `txt_scs_length`, 합성 데이터에 3만 개 중 227번 나온 연산)에서 모델은 숫자 세기, 문장부호 제거 같은 연산을 낸다. "이항계수 제곱의 합"(정답 `central_binomial`, 같은 값)에서는 이름이 비슷한 `binomial_product_sum`에 확률 0.99를 준다. 모델은 단어가 문구와 겹치는 연산을 고른다. 그 연산이 예시를 재현하는지는 모델 안에서 계산할 수 없고, 정답이 빔 밖에 있으면 검증도 돕지 못한다.

합성 데이터에서 연산이 굶는지도 쟀다. 무작위 입력이 맞지 않아 합성 프로그램에 한 번도 나오지 않는 연산이 780개 중 43개였고, 실제 보류 과제 중 4개가 이런 연산을 쓴다. 원인의 일부일 뿐이다.

## 9. 한계와 다음

- 범위 밖 과제(엔진 실패의 3분의 2)는 읽기를 아무리 잘해도 닿지 않는다. 라이브러리 연산을 고차 함수·조건식·작은 상수로 조합할 수 있게 하면 얼마나 열리는지 재고 있다(SeedLM-3).
- 모델은 예시가 가르지 못하는 후보들 사이에서 고르는 법을 따로 배운 적이 없다. 생성 학습만 했기 때문이다. 예시를 똑같이 재현하는 오답 후보를 모아 대조 학습하면 순위가 나아지는지가 다음 실험이다.
- 보류 과제가 94개, 시험 분할이 151개라 2~3문제 차이는 오차 안이다. 시험 분할의 +2(엔진 68 → 70)는 고침 2 / 깨뜨림 0이지만 통계적으로 확인된 이득이 아니다.
