# SeedLM-36~37: assert 셋을 통과한 답은 얼마나 진짜인가 — 개발 과제를 엄격하게 채점하기

작성일: 2026-11-23. [SeedLM-34](seed_lm34.md), SeedLM-35(검토기)가 끝난 뒤, 교사 보류 과제에서 "맞는" 뼈대 후보를 직접 읽다가 시작했다. 개수를 세는 진단이라 측정 전 등록은 하지 않았다. 판정 기준을 바꾼 것이 아니라, 지금 기준이 얼마나 느슨한지 잰 것이다.

## 요약

- 과제의 사례 몇 개(교사 과제 입력 셋, 개발 과제 assert 셋)를 통과한 프로그램을, 정답 프로그램(교사의 식, 개발 과제의 참조 해답)과 탐침 입력 24개에서 비교했다. 둘 다 값을 내는 탐침에서 하나라도 다르면 **어긋남**으로 본다.
- 개발 과제에서 지금 시스템(엔진 + s5-var `pyx_override`)은 **69 → 58**, 엔진 혼자는 **65 → 56**이다. assert 셋을 통과한 답의 여섯에 하나가 탐침에서 참조 해답과 어긋난다. 코더의 동점 깨기(+2)는 엄격한 판정에서도 남지만, 빈자리 채우기와 덮어쓰기의 이득(+1, +1)은 사라진다.
- **다만 엄격한 판정은 아래쪽 한계다.** 학습 쪽 과제에서 어긋남 10개를 직접 읽어 보니, 프로그램이 정말 틀린 것은 3개, 참조 해답과 숨은 테스트가 볼 법한 곳에서 다른 것은 2개였다. 나머지 5개는 판정의 착시였다. 탐침이 과제의 정의역을 벗어났거나(소수 목록에 1, 이진 배열에 4, 정렬된 두 목록 병합에 정렬 안 된 입력), 참조 해답 자체가 틀렸다. 진짜 숫자는 두 판정 사이, 대략 가운데다(5절).
- 뼈대 탐색이 넓혔다고 본 도달도 대부분 우연이었다. 뼈대 탐색으로만 맞는 후보가 생긴 과제는 개발 과제 10개 중 4개, 교사 보류 과제 21개 중 8개만 진짜다.
- 엔진이나 후보 중 누군가 진짜로 맞히는 개발 과제는 76개가 아니라 **62개**다. 시스템(58)과의 차이, 즉 고르기의 몫은 4개뿐이다. 나머지 32개는 어디에도 맞는 프로그램이 없다. 그동안 "남은 문제의 상당 부분은 고르기"라고 읽었는데, 엄격하게 보면 남은 문제는 대부분 **도달**이다.

## 1. 판정

`scripts/seedlm36_true_reach.py`(후보), `scripts/seedlm4_tasks.py holdout --strict`(시스템의 방법들). 탐침은 보이는 예시의 인자로 만든 24개(`rulecoder.consensus.probe_inputs`, 결정적)이고, 참조 해답은 샌드박스에서 돌린다.

| 판정 | 맞음의 조건 |
|---|---|
| 느슨함 (지금까지) | 과제가 밝힌 사례를 모두 통과 |
| 엄격함, 어긋남 없음 | 위 + 둘 다 값을 내는 탐침에서 정답 프로그램과 다른 값이 하나도 없음 |
| 엄격함, 일치 | 위 + 그런 탐침이 셋 이상 |

탐침에서 한쪽이 예외를 내면 아무 증거도 아니다. 과제의 정의역 밖일 수 있기 때문이다. 정의역 밖에서 둘 다 값을 내고 다르면, MBPP+의 확장 테스트는 통과할 프로그램이 어긋남으로 잡힐 수도 있다. 그러니 느슨한 판정은 위쪽 한계, 엄격한 판정은 아래쪽 한계에 가깝다. 아래 표는 "어긋남 없음" 기준이다.

## 2. 지금 시스템의 방법들 (개발 과제 94)

| 방법 | 느슨함 | 엄격함 |
|---|---|---|
| 엔진 | 65 | **56** |
| s5-var 혼자 (`pyx_model`) | 57 | 47 |
| 엔진, 없으면 코더 (`pyx_fill`) | 66 | 56 |
| 코더가 엔진의 동점을 깸 (`pyx_tie`) | 67 | 58 |
| `pyx_tie_fill` | 68 | 58 |
| **지금 시스템 (`pyx_override`)** | **69** | **58** |
| 모든 후보를 코더 확률로 (`pyx_rerank`) | 65 | 52 |
| `pyx_margin` | 68 | 55 |

`reports/seedlm/holdout4_s5-var_strict.json`. 엄격하게 봐도 지금 시스템의 순위는 그대로 맨 위다(`pyx_tie`와 같음). 잠근 MBPP+ 시험의 72/151(48%)은 확장 테스트로 채점한 것이라, 개발 과제의 느슨한 73%보다 엄격한 62%에 가깝다(분할이 달라 난이도는 다르다).

## 3. 도달과 고르기 (SeedLM-32의 후보)

| | 교사 보류 139, 느슨함 → 엄격함 | 개발 93, 느슨함 → 엄격함 |
|---|---|---|
| 엔진이나 후보 중 누군가 맞음 | 95 → 80 | 76 → **62** |
| 후보 중 누군가 맞음 | 88 → 71 | 67 → 54 |
| ― 코더 자신의 빔 | 67 → 63 | 57 → 50 |
| ― 뼈대 탐색 | 71 → 49 | 46 → 35 |
| ― 뼈대 탐색으로만 | 21 → **8** | 10 → **4** |
| 엔진 | 36 → 33 | 65 → 56 |
| 여섯 코더 평균, 후보만 | 64 → 60 | 59 → 49 |
| 여섯 코더 평균, 시스템 (SeedLM-32) | 58 → 54 | 65 → 55 |
| 검토기 결합 (SeedLM-35), 후보만 / 시스템 | 67 → 64 / 59 → 55 | 58 → 48 / 65 → 55 |

`reports/seedlm/true_reach_no_conflict.json`, `true_reach.json`("일치" 기준, 개발 과제 도달 60).

교사 보류 과제에서 읽어 본 우연한 "정답"의 예: 켜진 전등(1인 비트)의 수를 세는 과제에 `(num_divisor_count(n) + num_unset_bit_count(n)) % 10`, 문장의 첫 단어가 마지막 단어보다 긴지 묻는 과제에 `len(a0.split()) > 1 and len(set(a0)) > 8`, 리스트의 가장 큰 원소가 가장 작은 원소보다 앞에 오는지 묻는 과제에 `a0[0] > a0[-1]`. 후보가 과제당 70개쯤 되면, 사례 셋을 우연히 통과하는 틀린 프로그램이 흔하다. 코더들은 이런 후보에 아주 낮은 확률을 줬다(−30 ~ −60). 고르기가 이들을 지나친 것은 실패가 아니라 옳은 판단이었다.

## 4. 읽기

1. **개발 과제의 느슨한 숫자는 위로 부풀어 있다.** 테스트 셋은 엔진처럼 연산 780개를 뒤지는 탐색에도, 후보 70개를 만드는 탐색에도 쉽게 뚫린다. 지금까지의 개발 과제 판정은 모두 이 기준이었다. 결론이 "못 미쳐 채택하지 않음"인 실험들은 엄격하게 봐도 결론이 같다(SeedLM-32의 시스템은 55로 지금 시스템 58보다 낮다).
2. **남은 틈은 고르기보다 도달이다.** 엄격하게 보면 개발 과제 94개 중 62개에만 맞는 프로그램이 어딘가에 있고, 시스템은 그중 58개를 고른다. 나머지 32개는 엔진도, 코더 여럿의 빔도, 뼈대 탐색도 맞는 프로그램을 내지 못한다. 앞서 엔진이 못 푸는 개발 과제를 교사가 분류했을 때, 설명과 보이는 예시만으로는 답이 정해지지 않는 과제가 9개였다(SeedLM-3). 그런 과제는 어떤 방법으로도 닿기 어렵다.
3. **앞으로의 판정.** 개발 과제는 두 판정을 함께 보고한다. 엄격한 판정에는 착시가 섞여 있으므로(5절) 어느 한쪽만으로 결정하지 않는다. 채택하려면 느슨한 판정에서 지금 시스템(69)보다 나빠지지 않고, 엄격한 판정에서 지금 시스템(58)을 넘어야 한다. 검증 관문과 잠근 시험은 원래 확장 테스트로 채점하므로 그대로다.

## 5. 판정의 타당성과 엔진 안에서 고르기 (SeedLM-37)

`scripts/seedlm37_engine_strict.py`, `reports/seedlm/engine_strict_train.json`. 학습 쪽 실제 과제 434개(엑스트라 풀의 학습 부분, 참조 해답 있음, 개별로 읽어도 되는 과제)에서, 배포된 시스템이 부르는 그대로 엔진을 돌려 일치 프로그램을 40개까지 받고 하나하나를 두 판정으로 채점했다.

| 학습 쪽 434 | 느슨함 | 엄격함 |
|---|---|---|
| 엔진의 첫 답 | 320 | 271 |
| 엔진의 일치 40개 중 누군가 | 330 | 283 |

첫 답이 assert는 통과하지만 탐침에서 어긋나는 과제가 49개였다. 그중 엔진의 다른 일치가 엄격하게 맞는 것은 8개, 첫 답이 틀렸는데 다른 일치가 엄격하게 맞는 것은 4개다. 엔진 안에서 순서를 아무리 잘 바꿔도 얻는 몫은 12개(2.8%)가 한계라, 이 방향은 접는다. 우연히 통과한 답 대부분에는 맞는 대안이 엔진의 일치 안에 아예 없다.

어긋남 49개 중 10개를 무작위로 읽었다.

| 읽은 결과 | 수 | 예 |
|---|---|---|
| 엔진의 프로그램이 틀림 | 3 | "짝수 패리티"를 `a0 % 2 == 0`으로 |
| 숨은 테스트가 볼 법한 곳에서 참조 해답과 다름 | 2 | 여러 칸 공백을 줄일 때 끝 공백, 길이가 같은 목록 중 어느 것 |
| 착시: 탐침이 정의역 밖 | 4 | 소수 목록에 1, 이진 배열에 4, 정렬된 두 목록의 병합에 정렬 안 된 입력, 삼각형이 아닌 표 |
| 착시: 참조 해답이 틀림 | 1 | 자릿수 비교를 부동소수 나눗셈으로 한 참조 해답 |

표본이 작지만, 엄격한 판정의 어긋남 가운데 절반쯤은 진짜다. 그러니 개발 과제의 진짜 숫자는 지금 시스템 58~69, 엔진 56~65 사이 어딘가이고, 엔진이나 후보 중 누군가 맞히는 과제도 62~76 사이다. 고르기의 몫(도달과 시스템의 차이)은 어느 판정에서도 4~7개로 작고, 어디에도 맞는 답이 없는 과제는 18~32개다. "남은 틈은 고르기보다 도달"이라는 읽기는 두 판정 모두에서 선다.
