# 세션 분리와 인수인계

대화를 길게 유지하는 대신 저장소를 장기 기록으로 사용한다. 역할 분리는 새 채팅에서 독립 작업을
시작하기 위한 설계이며, 여러 에이전트를 자동으로 띄우는 설정은 아니다.

2026-11-04에는 사용자의 명시적 요청에 따라 S0/I01·S2/R01·S3/L01 작업 세션을 분리했다.
이번 실제 브랜치/worktree와 GitHub 이벤트 연동은 [협업 운영 기록](COLLABORATION.md)을 따른다.

## 역할과 쓰기 범위

| 역할 | 맡을 일 | 주로 수정하는 곳 | 넘길 결과 |
|---|---|---|---|
| S0 통합/계약 | 현재 상태·우선순위·충돌 조정·변경 통합 | `AGENTS.md`, `PROJECT_CONTRACT.md`, `contracts/`, `docs/project/`, 공통 CLI | 계약 버전, 결정 기록, 검증된 통합 커밋 |
| S1 원문/추출 | 수정본·쪽·표·각주·해시 확인, 자료 복원 | `data/sources.jsonl`, 수집/추출 스크립트, 근거 검수 자료 | 원문 manifest, 조항/표 fixture, 추출 누락 기록 |
| S2 검색/전처리 | 범위 필터·질의 정리·근거 검색 개선 | 검색/전처리 모듈과 해당 개발 실험 | 고정 입력/출력, Recall@k, 기존 방식과 차이 |
| S3 규칙/계산/문답 | 적용 조건·예외·unknown·계산·필요 질문 | `policy_rules.py`, `costs.py`, 문답 모듈, `config/grounding_rules.json` | 원문 연결 규칙, 경계 사례, 부분 결론 |
| S4 모델 실행/출력 | llama.cpp·프롬프트·스키마·생성 실패 처리 | `serve.sh`, `rag_v2.py`, 실행 설정, 출력 검증 관련 코드 | 설정 manifest, 반복/잘림·지연·토큰 비교 |
| S5 평가/감사 | 분할·동결·채점·검수 절차·회귀 보고 | 평가 스크립트, 새 평가 데이터, 새 reports | 잠금 파일, 오류별 지표, 검수/누출 기록 |
| H1 독립 사람 검수 | 공식 원문으로 먼저 답하고 불일치 조정 | 별도 검수 사본, 검수 기록 | 실제 검수자·날짜·근거·수정/제외 사유 |

S1–S5의 AI 검토는 H1을 대체하지 않는다. 최종 연구 평가의 독립 검토자 2명·불일치 조정은
기존 [실험 설계](../experiment_design.md)의 목표이며 아직 수행하지 않았다.
`chat.py`, `grounded_assistant.py`, 공통 스키마를 여러 역할이 동시에 바꿔야 하면 S0가 순서를 정한다.
필요한 범위 안에서 담당을 합칠 수 있지만 인수인계에는 실제 담당과 변경 범위를 적는다.

## 한 세션의 절차

1. 새 세션은 AGENTS → 계약 → STATE → 작업 카드 한 개 → 직전 인수인계 순서로 읽는다.
   목표는 작은 시작 문맥이다. 작업에 필요한 코드·원문을 추가로 읽는 데 임의의 토큰 상한을 두지는 않는다.
2. `git status --short --branch`와 작업 경로를 확인하고 역할·작업 ID·기준 커밋을 선언한다.
3. 작업 카드의 범위/완료 조건에 맞춰 구현한다. 새 발견이 범위를 넓히면 별도 카드로 기록한다.
4. 해당 검증을 수행하고 실행하지 않은 검증을 명시한다. 고정 평가 파일은 덮어쓰지 않는다.
5. 인수인계 파일을 남기고 브랜치를 push한다. 통합자가 상태/계약/현재 인수인계 포인터를 갱신한다.

끝내지 못한 세션도 `blocked` 또는 `partial`과 재개 명령을 기록한다. 컨텍스트가 찬 뒤 기억을
복원하는 비용보다, 작업이 바뀌는 지점에서 새 세션을 여는 편을 우선한다.
인수인계에는 장문의 사고 과정 대신 결정·관측·근거 파일·실행 결과를 적는다.

## 브랜치와 자원

작업 브랜치 예: `s2/r01-retrieval` 또는 `s4/m01-output`.
기존 폴더에 미커밋 변경이 있으면 강제 checkout/reset하지 않는다. 새 worktree 예시는 다음과 같다.

```bash
git fetch origin
git worktree add -b s2/r01-retrieval /workspace/worktrees/mllm-s2 \
  origin/docs/project-contract-and-session-roles
```

이 명령은 새 작업의 예시다. 계약 1.0.0 최초 작성 때는 worktree를 만들지 않았으며,
이후 사용자 요청으로 만든 실제 경로는 [협업 기록](COLLABORATION.md)에 따로 남겼다.
동일 이름이 이미 있으면 기존 작업부터 확인한다. `main` 병합 후에는 S0가 시작 ref를 갱신한다.

- 모델 가중치는 읽기 전용으로 재사용할 수 있다. worktree별 의존성·색인은 기존 경로 가정을 먼저 확인한다.
- `outputs/`와 `runtime/`는 Git 제외이며 worktree 사이 자동 동기화되지 않는다. 산출물마다 run ID·경로·해시를 남긴다.
- 기존 평가 스크립트 중 고정 출력 경로를 쓰는 것이 있다. 경로 옵션이 있다고 가정하지 말고 새 실행 경로 지원을 먼저 준비한다.
- 같은 4 CPU·16GiB 호스트에서는 생성·학습·대형 색인을 동시에 실행하지 않는다. S4가 점유 작업·종료를 인수인계한다.
- 이 자원 조정은 현재 **운영 규칙**이다. 작업 큐·분산 잠금·자동 스케줄러가 구현된 것은 아니다.
- 다른 세션/컨테이너의 `127.0.0.1:8080`은 같은 서버가 아닐 수 있다. health·모델명·실행 설정을 다시 확인한다.

## 새 채팅에 붙여 넣을 문장

```text
저장소 LeeDongHyun00/MyLittleLLM의 docs/project-contract-and-session-roles 브랜치에서 이어서 작업해.
AGENTS.md, PROJECT_CONTRACT.md, docs/project/STATE.md를 읽고
contracts/project.json의 latest_handoff를 확인해.
이번 역할은 S2, 작업은 docs/project/TASKS.md의 R01이야.
선행 D01 결과가 있는지 확인하고 없으면 공개 개발 근거 확인부터 진행해.
기존 고정 평가를 덮어쓰지 말고, 작업 결과·검증·남은 문제·다음 명령을 새 인수인계로 남겨.
```

역할/작업을 바꾸려면 S2/R01 두 항목만 해당 카드로 바꾼다. 모든 과거 논문과 채팅을 다시 첨부할 필요는 없다.

## 인수인계 형식

[TEMPLATE.json](../handoffs/TEMPLATE.json)을 복사한다. `code_baseline`은 작업 시작 커밋,
`branch`는 결과를 올리는 브랜치다. 최종 커밋은 해당 브랜치의 Git 이력에서 확인한다.
`verification`에는 명령·결과·실행 여부를, `next_tasks`에는 준비 상태와 필요한 입력을 적는다.
`open_questions`가 비어 있어도 사람 검수 등 미완료 항목은 `known_limits`에 남긴다.

코드/데이터 역할이 끝날 때 인수인계를 새 파일로 추가하고 S0가 `latest_handoff`를 갱신한다.
동시 진행 시 각 역할의 인수인계 파일을 보존하고, 최신 통합 인수인계에서 그 경로들을 연결한다.
