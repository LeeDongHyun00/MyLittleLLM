# Qwen3-4B의 설정·도구·입력 전처리 보완 조사

조사일: 2026-11-02. 대상은 현재 CPU 4코어·16GiB 환경의 Qwen3-4B Q4_K_M 입시·장학 상담이다.

**추가 학습 전에 출력 예산, 검색 결과 선택, 적용 범위를 보존하는 전처리를 먼저 개선할 근거가 있다.** 현재 오류에는 출력 잘림과 근거 누락·잘못된 전형/학기 선택이 섞여 있다. 설정 하나로 모두 해결되지는 않는다.

이번에는 공식 기술 문서와 연구를 확인하고, 기존 검색 기록에 대한 모델 호출 없는 진단을 실행했다. 아래 설정은 후속 실험 후보이며 운영 기본값을 변경하지 않았다. Docling·PaddleOCR 설치나 새로운 답변 정확도 실험을 완료했다는 의미도 아니다.

## 1. 실제 기록에서 확인한 병목

[이전 평가](../reports/rag_v2_report.md)의 네 조건은 모두 출력 한도가 160토큰이었다. 기존 BM25 조건의 13/16개 출력이 잘렸다. 일반 CLI 기본값은 384토큰이므로, 기존 평가의 낮은 통과율을 정상 CLI 기본 설정의 정확도로 해석하면 안 된다. 짧은 프롬프트·JSON 스키마를 적용하자 출력 완성은 개선됐지만, 검색의 조항 패턴 적중은 BM25의 12/16에서 새 검색의 8/16으로 감소했다.

이미 확인한 16문항을 개발 자료로 취급해 검색을 다시 진단했다. 질문·범위 또는 기존 후보 순위로 문서를 선택하고, 선택이 끝난 뒤 기존의 고정 `support_patterns`로 채점했다. 정답 페이지를 검색 결과에 강제로 넣지 않았다.

| 입력 후보 구성 | 조항 패턴 적중 | 문맥 문자 수 중앙값 |
|---|---:|---:|
| 기존 BM25 상위 2개 | 12/16 | 1,550 |
| 기존 BM25 상위 4개 | 13/16 | 2,994.5 |
| 기존 BM25 상위 8개 | 14/16 | 5,943.5 |
| 새 검색이 실제 선택한 구간 | 8/16 | 971.5 |
| 새 검색의 기존 후보 8개를 모두 유지 | 14/16 | 1,832.5 |
| 기존 후보 8개의 부모 문단을 모두 유지 | 15/16 | 4,355.5 |
| 실제 선택 구간을 해당 페이지 전체로 확장 | 9/16 | 2,307 |
| BM25 상위 2개 + 새 검색의 실제 선택 구간 | 15/16 | 2,467.5 |

이는 **검색 문맥의 패턴 포함 여부에 대한 사후 진단이며 답변 정확도가 아니다.** 확장 조건에는 기존 900토큰 제한을 적용하지 않았다. 문자 수는 토큰 수와 다르고, 문맥 길이·검색 방식이 통제된 효과 비교도 아니다. 기존 점수의 문서 수준 범위 검사와 정규식 한계를 그대로 갖는다. 올바른 전형·학기·예외 관계까지 검증한 15문항이라는 뜻이 아니다.

그럼에도 현재 최종 선택에서 잃는 근거가 많다는 점은 분명하다. 더 큰 임베딩 모델을 도입하기 전에 후보 선택과 문맥 구성을 점검할 이유가 있다. 이미 선택한 페이지를 통째로 늘리는 방법은 8→9문항에 그쳐, 잘못된 페이지 선택까지 해결하지 못했다. E04의 등록금 최종 납부 시각은 위 모든 구성에서 패턴을 찾지 못했다.

- E06: 부산대 2026 PDF 30페이지를 찾았지만 선택된 부모 문단이 입학 취소 후 3년 제한 조항 앞에서 끝났다. 같은 페이지 확장으로 패턴을 회복했다.
- E07: 검정고시 출신 논술전형의 성적증명서 제출 예외 대신 다른 전형의 서류 규정을 선택했다. 전형별 적용 범위가 필요하다.
- H05: 1학기 문서에 포함된 2학기 계획표가 검색됐다. 문서 전체에 `semester=1`을 붙이는 방식으로는 막을 수 없다.
- H01: 증빙 5년 보관 조항이 없는 문맥에서 10년이라는 답 또는 별도 제출 기한이 생성됐다. 인용 ID가 존재하는지만 검사해서는 발견하지 못한다.

재현: `python scripts/audit_preprocessing_options.py --output outputs/preprocessing-audit-repeat.json`

[진단 코드](../scripts/audit_preprocessing_options.py)와 [문항별 결과·입력 해시](../reports/preprocessing_audit.json)를 함께 보존했다. 기존 평가 파일은 수정하지 않았다.

## 2. 설정만으로 먼저 비교할 것

아래 값은 최적값이 아니라 개발 실험의 시작점이다. 한 단계씩 바꾸고, 통과율뿐 아니라 지연·토큰·잘림·잘못된 적용 범위를 함께 측정한다.

| 우선순위 | 현재 상태 | 비교 후보 | 기대하는 개선과 한계 |
|---|---|---|---|
| 1 | 평가 `max_tokens=160` | 동일 입력에서 384, 필요하면 512 | JSON이 끝나기 전 잘리는 문제. 근거 없는 답은 고치지 못함 |
| 1 | BM25 + 기존 긴 출력 지시 | BM25 + 짧은 답변 지시 + JSON 스키마 | 검색을 유지하면서 출력 개선의 효과를 분리. 이전에 측정하지 않은 조합 |
| 2 | 후보 8개에서 최종 2개, 근거 예산 900토큰 | BM25와 의미 검색 결과 합집합, 최종 3/4개, 예산 1,400/1,800토큰 | 후보 누락 완화. 실제 Qwen 토큰으로 계산하고 예산 초과 시 조항을 중간에서 자르지 않음 |
| 2 | 192토큰 leaf를 재정렬 | 제목·적용 범위·예외를 포함한 완결 조항 재정렬 | 짧은 구간의 관련성 점수가 답변에 필요한 근거 전체를 대표하지 못하는 문제 |
| 3 | 재정렬 후보 8개 | 16개, 필요하면 32개 | 후보 8개 안에도 근거가 많았으므로 최종 선택을 먼저 고친 뒤 비교. CPU 지연 증가 가능 |
| 3 | `temperature=0`, thinking 꺼짐 | 현재 결정적 조건과 공식 비사고 샘플링 설정 비교 | 온도 0이 사실 정확도를 보장하지 않음. 확률적 조건은 여러 seed로 반복 |

[Qwen 공식 모델 카드][qwen]는 비사고 모드에 `temperature=0.7`, `top_p=0.8`, `top_k=20`, `min_p=0`을 권장한다. 현재의 온도 0은 결정적 비교를 위한 선택이지 공식 최적 권장값은 아니다. 다만 공식 권장값이 이 한국어 입시 RAG에서도 더 정확한지는 별도 검증해야 한다. 잘못 검색한 문서를 샘플링 조정으로 복구할 수는 없다.

비사고 모드를 우선 유지한다. 사고 모드는 별도 실험으로 두고 사고·최종 답변을 포함한 출력 예산과 시간을 기록한다. 실제 서버 문맥 한도 8,192토큰에서 시스템 지시·질문·예시·근거·출력을 모두 계산한다. `max_tokens` 확대와 서버 문맥 길이 확대는 서로 다른 설정이다. 현재 작업에 장문 확장용 YaRN을 추가할 근거는 없다.

[llama.cpp][llama]의 JSON 스키마 제약은 형식을 제어한다. 스키마에 맞는 거짓 답도 가능하므로 사실 검증과 분리한다. 반복 현상이 재현될 때만 반복 억제 설정을 비교하며, 숫자·기관명까지 반복을 억제해 누락시키지 않는지 확인한다.

## 3. 모델에 들어가기 전의 전처리

### 문서 변환: PDF 유형에 맞게 추출

텍스트형 PDF에는 현재 pypdf 추출을 기준으로 두고, 표가 깨지는 페이지에 [pdfplumber][pdfplumber]의 문자 좌표·표 추출·시각 검사를 비교한다. 이 도구는 디지털 생성 PDF에 적합하며 스캔 문서의 OCR을 대신하지 않는다.

[Docling][docling]은 문서 구조에 기반한 분할과 메타데이터 결합을 제공한다. 표를 나눌 때 머리글을 반복하는 `repeat_table_header=True`, 넘칠 때 머리글을 빼지 않는 `omit_header_on_overflow=False`를 후보로 삼는다. 먼저 실패 페이지 소수에서 행·열·각주 대응을 원본과 대조한다. 도구를 쓰는 것만으로 병합 셀이나 한국어 각주의 해석이 정확해지는 것은 아니다.

스캔·문자 누락 페이지에만 [PaddleOCR의 한국어 인식 모델][paddle]을 비교한다. 공식 문서에 `korean_PP-OCRv5_mobile_rec`의 한국어·영어·숫자 인식 지원과 CPU 측정이 명시돼 있다. 이는 인식 모듈에 대한 정보이고, 전체 PDF 표 복원 시간이나 본 문서에서의 정확도를 뜻하지 않는다. 한국어 인식 모델을 선택해도 표 행·열 연결은 별도 검사한다.

문서 변환과 OCR은 수집 시 오프라인으로 실행하고 결과를 캐시한다. 16GiB 환경에서 생성 서버·임베딩·재정렬·OCR 모델을 동시에 올리는 방식은 피하고 단계별 최대 메모리를 측정한다.

### 표·조항 단위의 적용 범위

학년도·대학·학기·전형·지원자 유형·적용 기간을 **문서 전체뿐 아니라 절·표 행·조항에도** 붙인다. 일반 규정과 예외 규정을 연결하고, 제목과 각주가 어느 행에 적용되는지 저장한다. 원본 해시·PDF 페이지·좌표 또는 원문 오프셋도 유지한다.

전처리 레코드의 개념 예시는 다음과 같다. 아래는 설명용 구조이며 실제 검수 완료 레코드가 아니다.

```json
{
  "academic_year": 2026,
  "institution": "부산대학교",
  "admission_track": "논술전형",
  "applicant_type": "검정고시 출신",
  "subject": "검정고시 성적증명서 제출",
  "required": false,
  "conditions": ["온라인 제공이 되지 않아 서류를 제출하는 경우"],
  "scope_review_status": "needs_review",
  "source_id": "pusan-2026-susi",
  "pdf_page": 24
}
```

출처 문구·위치를 검수한 뒤 이 레코드와 실제 원문 조항을 함께 제공한다. 다른 전형의 '성적증명서 제출' 규정과 섞이지 않게 하는 것이 목적이다. 표에 `2학기`가 한 번 등장했다는 이유로 페이지 전체를 삭제해서도 안 된다. 같은 페이지가 두 학기를 모두 다룰 수 있으므로 적용 범위를 모르면 `unknown`으로 남겨 확인 대상으로 보낸다. 추정 메타데이터를 확정값으로 필터링하면 정답 근거 자체를 잃는다.

### 제목을 붙이고, 예외를 함께 보존

검색용 텍스트 앞에 검수된 대학·학년도·전형·절 제목을 붙인다. [Contextual Retrieval][contextual]은 각 구간의 문맥을 임베딩과 BM25 입력에 보충하는 접근을 설명한다. 이 프로젝트에서는 먼저 원문 제목과 구조에서 확인한 정보를 사용한다. 별도 LLM이 만든 설명을 사용한다면 검수 전에는 공식 근거로 취급하지 않는다. 해당 연구의 다른 데이터셋에서 나온 개선율을 Qwen3-4B 입시 상담의 예상 개선율로 사용하지 않는다.

텍스트 정규화는 원문과 검색용 버전을 분리한다. 공백·유니코드·날짜 표기를 정리하되 '아니', '제외', '면제', '단', '이내', '부터'를 삭제하지 않는다. 표의 수치만 뽑고 열 제목을 잃거나, 문장을 나누면서 바로 뒤의 예외를 버리는 처리를 막아야 한다.

## 4. 붙일 도구: 조건 확인과 계산을 코드로 수행

검수된 규칙을 JSON 또는 SQLite에 저장하고, Python에서 조건과 계산을 처리한다. 날짜·금액·기간·필수 서류처럼 구조화할 수 있는 항목이 우선 대상이다. 현재 주거비 계산기는 이런 방향의 출발점이며, 새 검색 경로에는 이 계산을 연결하는 작업이 남아 있다.

예를 들어 '신청일 전 1개월'은 무조건 30일을 빼면 안 된다. 원문의 달력 기준·말일 처리·예외를 확정한 뒤 코드로 계산해야 한다. 장학금 상한도 대상 자격·지원 기간·첫 달 예외가 확인된 경우에만 계산한다. 조건이 없는 상태에서 계산기만 붙이면 잘못된 답을 더 일관되게 만들 수 있다.

LLM에는 질문과 함께 적용 범위, 검증된 사실, 원문 근거, 코드 계산 결과를 담은 입력을 준다. LLM의 역할은 이를 설명하는 것이다. 답할 근거가 부족하면 추가 검색을 한 번 수행하거나 필요한 조건을 되묻고, 여전히 부족하면 확정 답변을 보류한다.

[Sufficient Context, ICLR 2025][sufficient]는 문맥 자체의 충분성과 모델의 문맥 활용 실패를 구분하고, 근거 충분성을 활용한 답변 보류를 연구한다. 작은 모델은 충분한 문맥에서도 틀릴 수 있으므로 전처리만으로 모든 오류가 사라지는 것은 아니다. Qwen의 자기 확신 점수나 재정렬 점수를 검증 없이 정답 확률로 취급하지 않는다.

생성 이후에는 답변의 숫자·단위·적용 범위·부정 여부를 근거와 대조한다. 이는 **후처리**다. 현재의 '인용 ID 존재' 검사에 더해 필요한 검증이며, 단순 정규식만으로 모든 의미적 함의를 판정할 수는 없다.

## 5. LLMLingua-2의 위치

[공식 LLMLingua-2 API][lingua]에는 `force_tokens`, `force_reserve_digit` 옵션이 있다. 다만 숫자를 남겨도 그 숫자가 어느 전형·학기·상한에 해당하는지는 잃을 수 있다.

현재 구현은 중요 조항 전체를 보호하고 손상 시 원문으로 복귀한다. 이전 실험의 토큰 감소는 1.93%였으므로 압축률을 높이기 위해 보호를 풀기보다, 먼저 관련 없는 표 행·중복 구간을 제거하는 편을 우선 검토한다. 규칙·조건·예외·출처는 압축하지 않고 부가 설명에만 선택적으로 적용한다. 의미 보존 검사를 통과하지 못하면 압축하지 않는다. 이 단계는 새로 적용하거나 재평가하지 않았다.

권장 처리 순서는 다음과 같다.

```text
PDF 수집·버전 확인 → 표/조항 추출 → 적용 범위·예외·출처 검수
→ 질문의 학년도·전형·학기 확인 → BM25 + 의미 검색
→ 범위 검사·중복 제거·완결 조항 선택 → 규칙 조회·계산
→ 근거 충분성 확인 → 선택적 압축 → Qwen의 설명 → 사실·인용 검증
```

## 6. 다음 평가의 순서

1. 기존 BM25 입력을 유지하고 출력 160/384토큰을 비교한다. 그다음 같은 384토큰에서 짧은 프롬프트·스키마의 효과를 비교한다.
2. 선택된 생성 설정을 고정하고 BM25, 기존 새 검색, 두 결과의 합집합을 같은 최종 근거 예산에서 비교한다. 별도로 예산을 늘린 조건을 측정해 검색 효과와 입력량 효과를 구분한다.
3. 표·조항·전형·학기 전처리를 적용한 색인과 기존 색인을 같은 검색·생성 설정에서 비교한다. 단계별 변경을 기록한다.
4. 검수된 규칙과 계산 도구, 근거 부족 시 확인 질문을 추가한다. 틀린 단정 비율과 답변 가능한 질문의 보류율을 함께 측정한다.
5. 선택을 마친 뒤 설정을 잠그고 새 규칙 그룹의 시험셋을 사용한다. 이미 분석한 16문항은 개발용 회귀 검사로 남긴다. 같은 문항으로 튜닝한 결과를 새 시험 정확도로 보고하지 않는다.

후속 시험에는 서로 다른 전형의 유사 규정, 1·2학기 혼합 표, 일반 규정과 예외, 연도 변경, 계산, 근거가 없는 질문을 포함한다. 정답 의미와 근거 적용 범위를 독립 검수하고, 검색 재현율·형식 유효율·사실 정확도·인용 타당성·잘못된 단정·응답 지연·최대 메모리를 분리해 보고한다.

현재 가장 먼저 실행할 조합은 **BM25 + 짧은 프롬프트·스키마 + 출력 384토큰**이다. 이어서 **BM25 근거를 유지하는 후보 병합과 조항·전형·학기 전처리**를 검증한다. 생성 모델의 양자화 등급을 올리거나 재학습하는 효과는 이 진단에서 측정하지 않았다.
