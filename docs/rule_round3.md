# 3차 교사 라운드: 못 푸는 문제를 찾아 규칙으로 만들기

작성일: 2026-11-18. [규칙 증류 가능성 검토](rule_distillation_feasibility.md)의 후속이다. 앞의 두 라운드는 교사 하나가 학습 분할의 실패를 보고 규칙을 썼다. 이번에는 실패를 더 넓게 모으고, 규칙 쓰기를 교사 서브에이전트 다섯에게 나누고, 총괄이 품질 검사·선별·평가를 맡았다. 측정은 모두 이 저장소 환경(CPU 4코어)에서 했다.

## 요약

1. **못 푸는 과제를 모아 규칙으로 만들었다.** 학습 분할과 MBPP+ 밖의 MBPP 과제에서 규칙 엔진이 못 푸는 489건을 다섯 범주로 나눠, 교사 서브에이전트 다섯이 병렬로 연산 456개를 썼다. 총괄이 자동 검사와 데이터 선별을 거쳐 452개를 남겼다.
2. **모델 없이 도는 규칙 엔진은 확실히 강해졌다.** 잠근 시험 분할 151문제에서 57 → 68문제(37.7% → 45.0%), 고침 11 / 깨뜨림 0. 검증 분할은 16 → 19문제. 이제 0.5B 학생 단독(56문제)보다 많이 푼다.
3. **학생 모델과 합친 파이프라인은 거의 오르지 않았다.** 1.5B는 97 → 98문제, 0.5B는 80 → 80문제.
4. **이유는 측정으로 드러났다.** 파이프라인의 남은 실패 가운데 70% 이상(1.5B 53건 중 38건)은 학생의 답이 보이는 예시를 통과하는데 숨은 테스트에서 틀리는 경우다. 엔진은 예시를 틀린 답만 대체하므로 여기에 닿지 않는다. 병목이 "답을 만들기"에서 "틀린 답을 알아보기"로 옮겨 갔다.
5. **원래 테스트가 모두 공개된 쉬운 조건에서도** 1.5B 98 → 99, 0.5B 83 → 84, 엔진 단독 59 → 70문제였다. 틀린 답을 더 많이 알아보지만, 그렇게 드러난 과제 대부분은 연산 두 개의 조합으로 풀리지 않는다.

## 1. 절차

```
[총괄]  실패 은행 만들기 ── 학습 분할 + MBPP+ 밖의 MBPP 과제(검증·시험과 비슷한 것은 자동 제외)
   │        규칙 엔진이 못 푸는 과제를 예시의 모양에 따라 다섯 범주로 나눈다
   ▼
[교사 서브에이전트 ×5, 병렬]  자기 범주의 실패만 보고, 자기 파일에만 연산을 쓴다
   │        수치 / 수열·리스트 / 문자열 / 중첩 구조 / 참·거짓 판정
   ▼
[총괄]  자동 검사 ── 탐색이 계산한 값 = 내보낸 코드의 값, 인자 불변, 참·거짓 연산은 잠금
   ▼
[총괄]  데이터로 선별 ── 개발 과제에서 연산마다 정답/오답 프로그램에 든 횟수를 세어 퇴출
   ▼
[총괄]  검증 분할 관문 ── 나빠지지 않았는지 확인한 뒤 라이브러리 동결
   ▼
[총괄]  시험 분할 평가 ── 한 번, 개수만
```

지킨 규칙:

- **검증·시험 분할은 교사가 볼 수 없다.** 교사에게는 자기 범주의 실패 은행 파일만 줬다. 교사용 점검 도구는 검증·시험 과제가 들어오면 실행을 거부한다.
- **교사는 자기 파일 두 개(연산 묶음, 보고서)만 고친다.** 연산 묶음은 `mylittlellm/rulecoder/oppacks/`에 범주별 파일로 들어가고, 어느 묶음을 쓸지는 `data/rule_pilot/operator_packs.json`이 정한다. 그래서 라운드 전체를 끄고 켜며 비교할 수 있다.
- **연산은 일반적이어야 한다.** 한 과제의 함수 이름이나 예시의 상수를 옮겨 적은 연산은 금지했다. 참·거짓을 돌려주는 연산은 반드시 키워드로 잠근다. 참·거짓 예시 하나는 술어의 절반이 우연히 맞히기 때문이다.
- **무엇을 남길지는 교사가 아니라 데이터가 정한다.** 퇴출 규칙은 교사가 연산을 쓰기 전에 정해 코드에 적었다(`scripts/round3_select.py`).

## 2. 실패 은행

| 출처 | 과제 | 핵심 라이브러리가 푸는 것 | 못 푸는 것 |
|---|---|---|---|
| MBPP+ 학습 분할(숨은 테스트로 채점) | 182 | 81 | 101 |
| MBPP+ 밖의 MBPP 과제(과제 자신의 assert 3개로 채점) | 528 | 140 | 388 |

추가 풀은 MBPP 974문제 가운데 MBPP+에 든 378문제를 빼고 만들었다. 검증·시험 과제와 함수 이름이 같거나 설명의 단어가 60% 이상 겹치는 65문제는 자동으로 뺐다. 실패 489건은 예시의 모양에 따라 다섯 범주로 나눴다: 수치 132, 수열·리스트 120, 참·거짓 판정 92, 문자열 77, 중첩 구조 59 (예시를 읽을 수 없는 9건은 제외). 핵심 라이브러리가 이미 푸는 221문제는 "깨뜨리지 않았는가"를 보는 회귀 세트로 썼다.

참·거짓 판정은 핵심 라이브러리에 해당 연산이 하나도 없어 학습 분할 29문제를 전혀 풀지 못하던 범주다.

## 3. 교사 다섯의 산출물

교사 다섯이 병렬로 일했다(각 50~65분). 셋은 일을 마친 뒤 모델 사용량 한도에 걸려 마지막 대화가 끊겼다. 연산 묶음과 보고서는 이미 디스크에 있었고, 총괄이 자동 검사와 회귀 확인을 다시 돌려 그대로 받았다.

| 범주 | 연산 수(잠금) | 학습 분할 실패 중 새로 푼 것 | 추가 풀 실패 중 새로 푼 것 | 회귀 세트에서 깨뜨린 것 |
|---|---|---|---|---|
| 수치 | 86 (85) | 20 / 23 | 57 / 109 | 0 |
| 수열·리스트 | 85 (84) | 15 / 21 | 66 / 99 | 0 |
| 문자열 | 54 (54) | 6 / 11 | 28 / 66 | 0 |
| 중첩 구조 | 62 (60) | 12 / 12 | 35 / 47 | 0 |
| 참·거짓 판정 | 169 (169) | 29 / 29 | 56 / 63 | 0 |

(각 묶음을 혼자 얹었을 때. 학습 분할 수치는 교사가 그 과제를 보고 연산을 썼으므로 일반화의 증거가 아니다.)

교사들이 스스로 한 일 가운데 기록해 둘 것:

- **기억에서 온 연산을 스스로 뺐다.** 세 교사가 "공개 벤치마크를 기억하고 있어 잠긴 분할의 과제를 떠올리며 연산을 만들 위험이 있다"고 보고하고, 은행 과제가 아니라 기억 때문에 넣은 연산을 지웠다(문자열 17개, 수치 5건, 중첩 구조 5건). 남은 것 가운데 교사가 "기억과 겹친다"거나 "은행 근거가 없다"고 표시한 3개는 총괄이 측정 전에 퇴출했다.
- **한 과제짜리 처방을 거절했다.** 수열 교사는 추가 풀 한 문제씩만 푸는 연산 4개를, 수치 교사는 6개 과제의 전용 처방을 넣지 않았다.
- **엔진의 한계를 보고했다.** 연산으로는 풀 수 없고 엔진을 고쳐야 하는 것: 동점 순위(세 교사), 설명에만 적힌 상수(두 교사), 길이 인자, `str(컨테이너)` 결과.

## 4. 품질 검사와 선별

**자동 검사.** 연산마다 탐색이 쓰는 함수와 답에 붙는 코드 조각이 따로 있다. 둘이 다르면 엔진이 검증한 프로그램과 내보낸 프로그램이 달라진다. `oplint`가 생성한 입력 수천 개에서 두 값(자료형 포함)이 같은지, 인자를 고치지 않는지, 두 번 호출해 같은지, 0.05초 안에 끝나는지, 참·거짓을 돌려주는 연산이 잠겨 있는지를 본다. 다섯 묶음 모두 결함 0이었다. 생성한 입력이 가드를 통과하지 못해 확인되지 않은 연산 19개는 해당 교사들이 손으로 만든 입력으로 같은 비교를 했다고 보고했다. 이 검사를 핵심 라이브러리에 처음 돌렸을 때 세 정의(Eulerian, Stirling, Delannoy 수)가 자기 가드 안의 입력에서 수 초씩 걸리는 것이 드러나 메모이제이션을 붙였다.

**엔진 옵션.** 교사가 요청한 엔진 변경은 모두 옵션으로 넣고, 켤지는 개발 과제 710개로 정했다(가장 많이 푸는 조합, 동점이면 작은 조합).

| 옵션 | 내용 |
|---|---|
| `tie_break` | 점수가 같은 프로그램 사이에서 모든 인자를 쓰는 것, 정의를 가진 것, 설명이 더 구체적으로 부른 것을 앞세운다. 전에는 발견 순서가 정했고 늘 오래된 연산과 단항 프로그램이 이겼다 |
| `description_constants` | 설명에 적힌 따옴표 문자열, 정수, 이름으로 부른 문자(space, comma …)를 탐색의 둘째 피연산자로 넣는다 |
| `keep_best` | 일치한 프로그램을 처음 40개만 남기지 않고 모두 순위를 매긴 뒤 자른다 |
| `named_pairs` | 설명이 부른 연산이 만든 두 수를 서로 결합한다 |

16개 조합 가운데 `tie_break` + `description_constants`가 556/710문제로 가장 많이 풀었다(옵션 없음 547). `keep_best`와 `named_pairs`는 보탬이 없어 끈 채로 뒀다.

**연산 퇴출.** 규칙은 교사가 연산을 쓰기 전에 정해 두었다. 잠그지 않은 연산은 맞은 최종 프로그램에 한 번 이상, 그리고 틀린 것만큼 이상 나와야 남는다. 잠긴 연산은 틀린 최종 프로그램에 두 번 이상, 맞은 것보다 많이 나왔을 때만 퇴출한다. 후보 453개 가운데 퇴출은 1개(`ends_with/2`, 맞음 0 / 틀림 2)였다. 최종 라이브러리는 핵심 328개 + 3차 452개 = 780개다.

**속도.** 연산이 2.4배가 됐지만 개발 과제 710개에서 가장 오래 걸린 탐색이 0.24초였다(시간 예산 2초). 결과가 시간 예산에 좌우되지 않는다.

## 5. 결과

순서는 미리 정했다. 라이브러리를 커밋한 뒤 검증 분할로 관문을 보고, 통과하면 동결해 시험 분할을 한 번 평가했다. 관문은 "엔진 단독과 1.5B 파이프라인 모두 2차 라이브러리보다 적게 풀지 않는다"였다.

| | 학습 182 (교사가 봄) | 검증 45 (관문) | 시험 151 (잠금) |
|---|---|---|---|
| 규칙 엔진 단독, 2차 라이브러리 | 81 | 16 | 57 (37.7%) |
| 규칙 엔진 단독, **3차 라이브러리** | **171** | **19** | **68 (45.0%)** |
| 고침 / 깨뜨림 | 91 / 1 | 3 / 0 | **11 / 0** |
| 1.5B 학생 + 분기-선택, 2차 | 146 | 29 | 97 (64.2%) |
| 1.5B 학생 + 분기-선택, **3차** | 162 | 31 | 98 (64.9%) |
| 0.5B 학생 + 분기-선택, 2차 | — | — | 80 (53.0%) |
| 0.5B 학생 + 분기-선택, **3차** | — | — | 80 (53.0%) |

- **모델 없이 도는 규칙 엔진은 시험 분할에서 11문제를 더 풀고 하나도 깨뜨리지 않았다.** 0.5B 학생 단독(56문제)을 넘어섰다.
- **새로 푼 11문제 가운데 7문제는 참·거짓 판정 묶음에서 나왔다.** 핵심 라이브러리에 해당 연산이 없던 범주다. 나머지 묶음은 시험 분할에서 거의 쓰이지 않았다(문자열 묶음은 한 번도). 잠긴 연산은 설명이 그 개념을 부를 때만 쓰이므로, 학습 분할에서 본 개념이 시험 분할에 다시 나와야 효과가 난다. 새 풀이에 쓰인 묶음 연산 9회 가운데 6회는 은행 과제를 위해 쓴 연산, 3회는 그 형제(반대 극성·다른 자료형) 연산이었다.
- **파이프라인은 거의 움직이지 않았다.** 이유는 아래 6절에서 센다.
- 학습 분할의 81 → 171은 교사가 그 과제를 보고 연산을 썼기 때문이다. 검증 분할(16 → 19)과 시험 분할(57 → 68)의 상승폭이 일반화의 추정치다.

## 6. 병목이 옮겨 갔다: 생성에서 검증으로

분기-선택 파이프라인에서 규칙 엔진은 학생의 답이 보이는 예시를 틀렸을 때만 쓰인다. 3차 라이브러리 뒤에 남은 실패를 나누면 다음과 같다(개수만 셌다).

| | 남은 실패 | 답이 보이는 예시를 틀림 (엔진이 개입하는 곳) | 답이 예시는 통과하지만 숨은 테스트에서 틀림 |
|---|---|---|---|
| 1.5B, 시험 | 53 | 15 | **38** |
| 0.5B, 시험 | 71 | 19 | **52** |
| 1.5B, 검증 | 14 | 4 | 10 |

남은 실패의 70% 이상이 오른쪽 열이다. 예시 하나로는 틀렸다는 것을 알 수 없으므로 엔진이 아무리 많은 과제를 풀어도 닿지 않는다. 시험 분할에서 엔진은 맞히고 1.5B 파이프라인은 틀린 과제가 3개 있는데, 셋 모두 학생의 답이 예시를 통과한 경우였다.

그러면 "학생의 답과 엔진의 프로그램이 둘 다 예시를 통과하면 엔진을 믿는" 규칙은 어떤가. 시험 분할에서 그런 과제 가운데 학생만 맞은 것이 24개, 엔진만 맞은 것이 3개다(검증 분할 4 대 1). 엔진의 프로그램은 예시를 우연히 재현한 것이 많다. 이 중재 규칙은 만들지 않았다.

정리하면, 이 구조에서 규칙을 더 쓰는 것은 "예시를 틀린 과제"를 줄이는 일이고, 그런 과제는 이제 시험 분할에서 15개 남았다. 다음 이득은 학생의 답이 틀렸다는 것을 알아내는 쪽(검증)에서 나와야 한다.

## 7. 원래 테스트가 모두 공개된 조건

MBPP의 원래 형식처럼 과제의 원래 테스트(보통 3개)가 모두 공개된 조건도 쟀다. 후보는 공개 테스트를 모두 통과해야 하고, 역추론은 첫 예시에서 출발해 일치한 프로그램을 순위대로 보며 공개 테스트를 모두 통과하는 것을 쓴다(`select --public base`). 채점은 그대로 숨은 테스트까지다. 예시 하나 조건보다 쉬운 별개의 조건이라 5절의 표와 섞지 않는다. 절차는 실행 전에 정해 두었고, 검증 분할과 시험 분할을 한 번씩 돌렸다.

| 시험 151문제 | 2차 라이브러리 | 3차 라이브러리 |
|---|---|---|
| 규칙 엔진 단독 | 59 (39.1%) | 70 (46.4%) |
| 1.5B 학생 + 분기-선택 | 98 (64.9%) | 99 (65.6%) |
| 0.5B 학생 + 분기-선택 | 83 (55.0%) | 84 (55.6%) |

검증 분할에서는 엔진 단독 16 → 19, 1.5B 파이프라인 29 → 31문제였다.

공개 테스트가 늘면 틀린 답을 더 많이 알아본다. 1.5B 파이프라인의 시험 분할 실패 가운데 "틀렸다고 드러난 것"이 예시 하나 조건의 15건에서 29건으로 늘었다. 그런데 3차 라이브러리가 그중 새로 푼 것은 1건이다. 개발 과제에서 교사들이 "연산으로는 안 된다"고 적은 사유(상태를 들고 도는 반복문, 동적 계획법, 여러 단계의 알고리즘)와 같은 종류일 것으로 추정한다. 시험 과제는 열어 보지 않았다.

## 8. 한계

- **교사도 벤치마크를 알고 있을 수 있다.** 교사 서브에이전트는 총괄과 같은 모델이고, MBPP는 공개 데이터다. 교사가 볼 수 있는 파일은 막았지만 교사가 원래 알고 있던 출제 경향까지 막지는 못한다. 그래서 시험 분할의 이득은 "보지 않은 과제로의 일반화"와 "교사의 사전지식"을 구별하지 못한다.
- **추가 풀과 시험 분할이 닮았을 수 있다.** MBPP에는 서로 비슷한 문제가 많다. 함수 이름이 같거나 설명의 단어 집합이 60% 이상 겹치는 추가 풀 과제는 자동으로 뺐지만, 그 기준을 피해 간 유사 문제가 남아 있을 수 있다. 누출은 아니어도 일반화의 증거로는 약해진다.
- **시험 분할을 라운드마다 다시 썼다.** 이 분할은 1·2차 라운드 평가에 이미 쓰였다. 과제 내용은 보지 않고 개수만 봤지만, 같은 분할로 여러 번 결정을 내리면 그 분할에 맞춰질 위험이 쌓인다. 이번 라운드에서 시험 분할을 보고 내린 결정은 없다(선별과 관문은 개발·검증 분할로 했다).
- **표본이 작다.** 시험 분할은 151문제, 검증 분할은 45문제다.
- **예시가 있어야 한다.** 엔진은 보이는 예시 하나에서 출발한다. 예시가 없는 요청에는 이 규칙들이 쓰이지 않는다.
- **연산이 늘수록 우연의 일치도 는다.** 파이프라인에서는 이미 틀린 답만 대체하므로 손해가 없지만, 엔진이 낸 프로그램이 "예시를 재현했다"는 사실이 정답을 뜻하지 않는다는 점은 그대로다.
- **범위 밖의 과제가 많다.** 상태를 들고 도는 반복문, 동적 계획법, 여러 단계의 알고리즘은 연산 두 개의 조합으로 표현되지 않는다. 교사들이 이런 과제는 건드리지 않고 사유만 적었다.
- **교사 셋은 마지막 대화가 끊겼다.** 모델 사용량 한도 때문이다. 산출물은 완성돼 있었고 총괄이 자동 검사와 회귀 확인으로 다시 확인했지만, 그 셋에게 마지막 질문(기억에서 온 연산이 남았는지)을 하지 못했다. 그 셋의 보고서에 적힌 자기 신고만 반영했다.
- **개발 과제의 학습 분할 수치는 낙관적이다.** 교사가 그 과제를 보고 연산을 썼다(엔진 단독 81 → 171문제).

## 9. 다음 단계

1. **틀린 답을 알아보는 쪽에 투자한다.** 남은 실패의 대부분은 예시를 통과하는 오답이다. 규칙 엔진의 프로그램을 기준으로 학생의 답을 뒤집는 중재 규칙은 시험 분할 기준 손해(24)가 이득(3)보다 커서 만들지 않았다. 대신 학생 모델에게서 답을 여러 개 받아 공개 예시와 서로의 일치로 고르는 방법(생성-검증)을 재 볼 만하다. 모델 호출이 늘어나는 만큼 CPU 시간이 든다.
2. **알고리즘형 과제를 위한 규칙 형식.** 연산 두 개의 조합으로는 반복문·동적 계획법을 표현할 수 없다. 교사가 "알고리즘 틀(템플릿)"을 쓰고 엔진이 그 틀의 빈칸을 예시로 채우는 형식이 다음 후보다.
3. **엔진 단독의 쓰임새.** 엔진은 이제 0.5B 학생보다 많이 풀고, 모델 없이 과제당 0.3초 안에 끝난다. 모델을 띄울 수 없는 환경에서는 그 자체로 쓸 수 있다.
