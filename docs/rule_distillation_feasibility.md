# 규칙 증류로 CPU 코딩 LLM을 만들 수 있는가: 가능성 검토

작성일: 2026-11-18. 논문 네 편(HypoGeniC, FeatLLM, RuleFit, Prose2Policy)을 읽고, 선행연구 수치를 원문에서 확인하고, 이 저장소 환경(CPU 4코어, GPU 없음)에서 예비 실험을 실행해 판단했다.

## 요약

1. **"규칙으로 CPU 모델을 코딩의 모든 기능에서 최상위 수준으로"는 성립하지 않는다.** 가장 쉬운 축인 단일 함수 작성에서도 1.5B 모델과 규칙 엔진의 합은 64.2%이고, 공개된 7B 수치는 71.7%다. 열린 과제에서는 격차가 훨씬 크다.
2. **규칙을 모델에게 읽히는 방식은 통하지 않았다.** 교사가 쓴 규칙을 프롬프트에 넣으면 학습 분할에서 115 → 107문제로 떨어졌고, 좁게 다듬은 2차 규칙과 오류 피드백 수리도 시험 분할에서 89 → 89문제로 제자리였다.
3. **규칙을 실행해서 확인하는 방식은 통했다.** 규칙을 지시가 아니라 가설로 다루는 분기-선택과 예시 역추론은 시험 분할에서 89 → 97문제(58.9% → 64.2%)로, 8문제를 고치고 한 문제도 깨뜨리지 않았다(p=0.008). 0.5B 학생에서는 56 → 80문제(37.1% → 53.0%)다. 역추론은 모델을 부르지 않고 CPU에서 과제당 0.1초 안에 끝난다.
4. **이득은 좁은 조건에서만 난다.** 보이는 예시가 있어야 하고, 답이 연산 두 단계로 표현돼야 한다. 역추론이 찾은 프로그램 중 숨은 테스트까지 맞은 것은 시험 분할에서 31%(16개 중 5개)였다.

처음부터 학습한 소형 모델에 대해서는 [SeedLM 문서](seed_lm.md)에 따로 적었다. 모든 수치는 `reports/rule_pilot/`의 결과 파일에서 나온다.

## 1. 질문을 세 주장으로 나눈다

검토 대상은 다음 구상이다. "규칙 기반 방식은 새 규칙을 사람이 계속 추가해야 한다. 이 약점을 생성형 AI가 규칙을 대신 쓰게 해서 보완하면(가중치가 아니라 규칙으로 옮기는 증류), 규칙을 이용해 코딩의 모든 기능을 최상위 수준으로 수행하면서 CPU에서도 동작하는 LLM을 만들 수 있다."

이 문장에는 서로 다른 주장 세 개가 들어 있고, 근거의 강도가 각각 다르다.

- **주장 A — 규칙 작성의 자동화.** 큰 생성형 모델(교사)이 실패 사례를 보고 규칙을 쓰고 갱신할 수 있다.
- **주장 B — 규칙을 통한 능력 이전.** 그렇게 만든 규칙이 CPU에서 도는 작은 모델(학생)의 코딩 정확도를 실제로 올린다.
- **주장 C — 전 기능 최상위.** 그 결과가 코딩의 모든 기능에서 최상위 모델 수준에 이른다.

## 2. 네 논문에서 가져올 것

| 논문 | 핵심 장치 | 이 구상에서의 역할 | 그대로 옮길 수 없는 이유 |
|---|---|---|---|
| HypoGeniC (Zhou 외, 2024) | 예시 10개로 초기 가설을 만들고, 학습 예시마다 상위 k개 가설을 평가해 보상 `정확도 + α·sqrt(log t / 사용 횟수)`를 갱신한다. 여러 가설이 틀린 예시는 **오답 은행**에 넣고, 은행이 10개 차면 그 예시들로 새 가설을 만들어 보상이 낮은 가설과 교체한다. | "규칙을 사람이 계속 추가해야 한다"는 약점을 자동화하는 뼈대. 실패 사례가 쌓이면 교사 모델이 규칙을 새로 쓰고, 성적이 나쁜 규칙은 밀려난다. | 가설을 **적용**하는 일도 LLM이 한다. 논문도 "LLM의 추론이 불완전해 가설 품질이 정확도에 그대로 반영되지 않는다"고 적었고, 부록에는 Mixtral이 옳은 가설을 만들고도 적용하지 않은 사례가 있다. 실험당 평균 1.5시간이 든다. |
| FeatLLM (Han 외, ICML 2024) | LLM이 클래스별 조건 규칙 10개를 쓰고, 다시 LLM이 그 규칙을 Python 함수로 바꾼다. 규칙 충족 여부(0/1)를 특성으로 삼아 음수가 될 수 없는 가중치의 선형 모형을 맞추고 20회 배깅 앙상블을 한다. | **규칙을 코드로 컴파일하면 추론 때 LLM이 필요 없다.** Adult 데이터에서 추론 0.006ms/건, LLM을 매번 부르는 방식은 335–523ms/건. CPU 동작이라는 목표와 직접 맞닿는다. | 표 데이터 분류다. 입력이 고정된 특성 벡터라 규칙이 `나이 > 50` 같은 술어로 닫힌다. 코드 생성은 출력이 열린 구조물이라 "규칙 충족 = 정답"이 되지 않는다. |
| RuleFit (Friedman & Popescu, 2008) | 트리 앙상블의 모든 노드를 규칙으로 꺼내 후보를 대량으로 만들고(500트리 × 10규칙 = 5,000개), 라쏘 회귀로 계수를 맞춘다. 계수의 80–90%가 0이 된다. 규칙 중요도는 `|계수|·sqrt(s(1−s))` (s는 규칙이 발동하는 비율). | 생성형 모델이 쓴 규칙은 질이 고르지 않다. **많이 만들고, 데이터로 걸러서, 소수만 남기는** 절차가 필요하다. | 저자들도 규칙만으로는 선형 함수를 근사하기 어려워 원래 변수를 선형 항으로 함께 넣었다. 규칙은 다른 표현과 섞어 써야 한다는 뜻이다. |
| Prose2Policy (Gupta & Sreenivasamurthy, 2026) | 자연어 정책 → 구성 요소 추출 → 스키마 검증 → Rego 생성 → 린트(Regal) → 컴파일(OPA) → 자동 생성 테스트. | 생성 결과를 **결정적 검증 단계**로 둘러싸는 구조. 수용한 389개 정책 중 95.3% 컴파일, 긍정 테스트 82.2%, 부정 테스트 98.9% 통과. | 같은 입력에도 출력이 달라질 수 있다고 저자가 명시한다. 긍정 테스트 실패의 주원인은 생성 코드가 아니라 **자동 테스트 생성의 한계**였다. 검증기가 약하면 루프 전체가 약해진다. |

네 논문을 합치면 하나의 순환이 된다. **실패 수집(HypoGeniC) → 교사가 규칙 작성 → 실행 가능한 형태로 컴파일(FeatLLM) → 데이터로 선별(RuleFit) → 결정적 검증으로 둘러싸기(Prose2Policy)**. 다만 네 논문 모두 분류이거나 형식이 좁은 번역 과제다. 출력 공간이 열려 있는 일반 코딩에 이 순환이 얼마나 통하는지는 논문만으로 알 수 없어 4절의 실험으로 확인했다.

## 3. 선행연구에서 확인된 사실

수치는 2026-11-18에 원문 페이지에서 직접 확인한 것만 적었다. 저자 보고 프리프린트는 그렇게 표시했다.

### 3.1 가설을 지지하는 결과

- **강한 모델이 쓴 규칙은 약한 모델로 옮겨 간다.** HtT(Zhu 외, arXiv 2310.07064)에서 GPT-3.5는 GPT-4가 귀납한 규칙 라이브러리를 쓰면 CLUTRR 정확도가 21.2 → 48.4가 됐다. 자기가 만든 규칙을 쓸 때(37.6)보다 높다. ExpeL(AAAI 2024)도 GPT-4가 뽑은 통찰을 GPT-3.5가 쓰면 HotpotQA 28.0 → 39.0, 통찰을 GPT-3.5가 뽑으면 32.0에 그쳤다.
- **실행 가능한 스킬은 4B급 모델에도 크게 통한다(저자 보고 프리프린트).** SKILL-DISCO는 GPT-4o가 만든 실행형 스킬 라이브러리를 그대로 줬을 때 Qwen3.5-4B의 ALFWorld 성공률이 61.2 → 91.0, SKILL-KD는 교사 궤적과 학생 실패를 대조해 만든 스킬 패치로 Qwen3.5-4B 평균이 43.5 → 66.8이 됐다고 보고한다. 둘 다 코딩이 아닌 에이전트 과제다.
- **프롬프트(규칙) 최적화가 가중치 학습을 이기기도 한다.** GEPA(ICLR 2026)는 Qwen3-8B에서 6개 과제 평균 45.23 → 54.85를 얻었고, 같은 모델의 GRPO 미세조정(24,000 롤아웃)은 48.91이었다. 롤아웃은 최대 35배 적게 썼다.
- **생성형 모델은 정적 분석 규칙을 쓸 수 있다.** KNighter(SOSP 2025)는 패치를 보고 Clang 정적 분석 검사기를 합성해 리눅스 커널에서 새 버그 92건(확인 77, CVE 30)을 찾았다. 커밋당 비용 약 0.24달러, 오탐률 약 35%. QLCoder는 CVE 176건 중 53.4%에 대해 올바른 CodeQL 질의를 합성했다.
- **검증·제약은 작은 모델의 수리 능력을 가장 많이 올린다.** 타입 제약 디코딩(Mündler 외, PLDI 2025)은 컴파일 오류를 HumanEval에서 74.8% 줄였고, Gemma-2-2B의 수리 과제 pass@1은 11.6 → 20.9(+79.4%)였다. 27B 모델의 향상은 +7.1%였다.

### 3.2 가설을 제한하는 결과

- **약한 모델은 자연어 원칙을 따르지 않는다.** LEAP(arXiv 2402.05403)는 GPT-4에서는 효과가 있었지만 "공개 모델로 한 예비 실험에서는 향상되지 않았다"고 적었다. Llama-2-chat-70B의 GSM8K는 CoT 52.5, GPT-4가 써 준 원칙을 줘도 49.8–51.0이었고, 원인으로 "시험 시점에 원칙을 따르지 않았다"를 들었다.
- **규칙 수가 늘면 작은 모델부터 무너진다.** IFScale(arXiv 2507.11538)에서 지시 100/250/500개일 때 준수율은 gemini-2.5-pro 98.4/84.8/68.9, gpt-4.1-nano 51.6/25.7/16.2였다. 작은 모델은 지수적으로 떨어진다. 10B 이하 공개 모델은 측정 대상이 아니었다.
- **합성한 규칙은 본 데이터에 과적합한다.** SecReason(2026-10, 프리프린트)의 Semgrep 규칙은 규칙을 만든 절반에서 재현율 97.0%, 나머지 절반에서 7.0%였다.
- **스스로 만든 지침은 오히려 해롭다.** SkillsBench(v4)에서 사람이 다듬은 스킬은 평균 +16.6%p, 모델이 스스로 생성한 스킬은 −8.1 ~ −11.5%p였다. 포괄적인 스킬(+0.7%p)보다 간결한 스킬(+19.0%p)이 나았다. "Evaluating AGENTS.md"는 컨텍스트 파일이 성공률을 올리지 못하고 비용만 20% 넘게 늘린다고 보고했다.
- **문법 수준 제약은 정답률을 거의 올리지 못한다.** SynCode는 구문 오류를 96% 없앴지만 pass@1은 LLaMA-7B 11.2 → 11.5, WizardCoder-1B 20.0 → 20.0이었다.
- **데이터가 조금만 있어도 가중치 학습이 프롬프트를 앞지른다.** "When Does Fine-Tuning Overtake Prompting?"(NeurIPS 2026 워크숍; Qwen3 0.6B/1.7B/4B, 17개 과제)은 라벨 약 50개부터 LoRA가 인컨텍스트 학습을 앞선다고 보고했다. Skill-to-LoRA는 스킬 문서를 프롬프트에 넣는 것보다 스킬별 LoRA가 5.2%p 높았다(Qwen3.6-27B).

### 3.3 "최상위 수준"까지의 거리

| 벤치마크 | CPU에 올릴 수 있는 급 | 최상위 | 출처 시점 |
|---|---|---|---|
| MBPP+ (단일 함수) | Qwen2.5-Coder 0.5B 43.7 / 1.5B 59.4 / 3B 62.4 / 7B 71.7 | 32B 75.1, GPT-4o 72.5 | 2024-11 기술 보고서 |
| LiveCodeBench v6 | Qwen3.5-4B 55.8 / 9B 65.6, Gemma 4 E4B 52.0 | GPT-5.2 87.7, Gemini-3 Pro 90.7 | 2026-02 모델 카드 |
| Aider polyglot (다중 언어 편집) | 14B 이하 등재 없음, Qwen2.5-Coder-32B 16.4 | gpt-5 (high) 88.0 | 2025-11 |
| SWE-bench Verified (실제 저장소 이슈) | 기본 Qwen2.5-Coder-7B 1.0, 증류한 SWE-Hero-7B 52.7 | Claude Opus 5 96.0 | 2026-07 |
| Terminal-Bench | 기본 Qwen3.5-9B 16.1, 강화학습한 9B 33 | 59.3 (2026-02) | 2026 |

단일 함수 작성은 7B급이 이미 2024년의 최상위 모델과 비슷하다. 과제가 길어지고 열릴수록 격차가 벌어져, 실제 저장소 이슈 해결에서는 대규모 증류를 거친 7B도 최상위의 절반 수준이다. 이 격차를 규칙으로 메웠다는 보고는 찾지 못했다. 강한 모델이 규칙 기반을 유지하고 CPU의 작은 모델이 그것으로 코드를 생성·수리하는 연구 자체를 찾지 못했다.

CPU 속도는 모델 크기가 정한다. 공개 측정값으로 1.5B급은 노트북 CPU에서 약 15토큰/초, 7B Q4는 2025년 노트북에서 10.5토큰/초, 구형 4코어 Xeon에서 3.2–4.5토큰/초다.

## 4. 예비 실험

논문과 선행연구는 분류·에이전트 과제의 결과다. 코드 생성에서 주장 B가 성립하는지 이 저장소의 CPU 환경에서 직접 측정했다. 규모가 작은 개발용 예비 실험이며 리더보드 제출용 평가가 아니다.

### 4.1 설계

| 항목 | 내용 |
|---|---|
| 환경 | Intel Xeon 2.1GHz 4코어(AVX-512), RAM 15GB, GPU 없음. llama.cpp `b11960`, 스레드 4, 슬롯 1, 컨텍스트 8,192 |
| 학생 | Qwen2.5-Coder-1.5B-Instruct `Q4_K_M` (1.1GB). temperature 0, seed 42, 최대 768토큰 |
| 교사 | 이 코딩 세션의 대형 생성형 모델. **학습 분할의 실패 사례만** 읽었다. |
| 과제 | MBPP+ v0.2.0 378문제. 학생에게는 한 문장 설명과 예시 `assert` 1개만 보인다. |
| 채점 | 원래 테스트(base)와 추가 숨은 입력(plus, 문제당 중앙값 105개)을 모두 통과해야 해결로 센다. EvalPlus 0.3.1의 채점 함수를 그대로 썼다. |
| 분할 | 학습 182 / 검증 45 / 시험 151 (48:12:40, 시드 고정, `data/rule_pilot/split.json`). 시험 분할은 실패 진단을 만들지 않아 교사도 작성자도 내용을 볼 수 없다. |

비교한 조건:

| 조건 | 프롬프트에 추가 | 실행 단계 추가 |
|---|---|---|
| `base` | 없음 (EvalPlus 표준 지시문) | 없음 |
| `advice` | 실패를 보기 전에 써 둔 일반 조언 10줄 (대조군) | 없음 |
| `rules` | 교사 규칙 중 발동 조건이 맞는 것 최대 6개 | 없음 |
| `base+autofix` | 없음 | 결정적 코드 수정 2종 (모델 호출 0회) |
| `verify` | 없음 | 구문 검사 → 프롬프트에 보이는 예시 실행 → 실패하면 오류 내용을 주고 다시 쓰게 함(최대 2회) |

`verify`의 수리 루프는 **프롬프트에 보이는 예시 하나만** 실행한다. 숨은 테스트는 최종 채점에만 쓰인다. 이 조건들이 통하지 않은 뒤에 만든 두 조건(`infer`, `branch`)은 5절과 6절에서 다룬다.

규칙을 만든 절차(네 논문의 장치를 순서대로 적용):

1. 학생의 기준선 답안을 채점해 학습 분할 실패를 오답 은행에 모은다 (HypoGeniC).
2. 교사가 실패를 하나씩 읽고 원인 하나를 붙인 뒤, 원인별로 규칙을 쓴다. 규칙마다 프롬프트에 대한 정규식 발동 조건을 달아 관련 과제에서만 보이게 한다 (FeatLLM의 "규칙을 실행 가능한 조건으로").
3. 과제마다 발동한 규칙의 무작위 절반만 넣어 다시 풀게 하고, 기준선 대비 결과 변화를 규칙 포함 여부에 라쏘 회귀한다 (RuleFit). 규칙별 보상은 HypoGeniC의 식으로도 계산한다.
4. 교사가 규칙별 성적과 남은 오답, 새로 깨진 과제를 보고 규칙을 퇴출·수정·추가한다 (HypoGeniC의 갱신 단계).
5. 결정적으로 고칠 수 있는 실패 유형은 프롬프트 규칙이 아니라 코드 수정으로 만든다. 탐침 검사기는 개발 데이터에서 정밀도를 재서 기준을 넘는 것만 쓴다 (Prose2Policy의 검증 관문).

### 4.2 기준선과 속도

규칙 없는 학생은 378문제 중 228문제(60.3%)를 숨은 테스트까지 통과했다. 원래 테스트만으로는 265문제(70.1%)다. 공개된 전정밀도 수치(MBPP 69.2, MBPP+ 59.4)와 거의 같아, 4비트 양자화와 이 하네스가 결과를 왜곡하지 않았다고 본다.

CPU 4코어에서 프롬프트 처리 약 226토큰/초, 생성 약 17.5토큰/초였다. 답 하나가 평균 95토큰이라 문제당 5.4초가 걸렸다.

### 4.4 1차 규칙: 프롬프트에 넣은 규칙은 해로웠다

교사는 1차로 규칙 27개를 썼다. 지식 규칙 15개(개념 키워드로 발동)와 행동 규칙 12개(그중 4개는 항상 발동)다. 과제마다 발동한 규칙의 무작위 절반을 넣어 학습 분할 182문제를 다시 풀게 했다.

- 해결 문제 수가 115 → 107로 줄었다. 고친 것 7건, 깨뜨린 것 15건.
- 보여 준 규칙 수별 평균 변화: 1개 +0.06, 2개 −0.06, 3개 −0.04, 4개 −0.14. **규칙이 늘수록 나빠졌다.**
- 규칙이 하나도 뽑히지 않은 9문제는 기준선과 답이 완전히 같았다(디코딩이 결정적임을 확인).

라쏘 계수(교차검증으로 고른 벌점 0.002)와 규칙별 성적:

| 규칙 | 내용 | 포함 횟수 | 고침/깨뜨림 | 라쏘 계수 |
|---|---|---|---|---|
| B04 | 빈 입력을 먼저 처리하라 (`if not items: return []`) | 52 | 2 / 9 | −0.123 |
| B01 | 함수 이름을 예시와 똑같이 | 86 | 2 / 10 | −0.030 |
| B03 | 예시와 같은 자료형·형태로 반환 | 97 | 4 / 9 | −0.023 |
| B02 | 예시가 어떻게 계산되는지 주석으로 먼저 쓰라 | 85 | 2 / 7 | +0.003 |
| B08 | 예시의 크기·지수를 하드코딩하지 말라 | 92 | 3 / 7 | 0 |
| B10 | 재귀에는 0에서 멈추는 기저 조건을 | 5 | 0 / 2 | −0.301 |
| B09 | 문자열·숫자 혼합 리스트는 숫자만 먼저 거르라 | 2 | 2 / 0 | +0.873 |
| K02 | 중심 다각수·별 수 공식 | 1 | 1 / 0 | +0.543 |

깨진 답을 읽어 보면 원인이 분명하다.

- **규칙 속 예시 코드를 그대로 베낀다.** B04의 `return []`를 따라 빈 튜플 뺄셈에서 `()` 대신 `[]`를, 튜플 크기 계산에서 40 대신 0을 반환했다. B10의 `return 0`은 지식 규칙이 알려 준 올바른 초기값 S(0)=1을 덮어썼다.
- **묶음 규칙의 내용을 섞는다.** 암스트롱·완전수·친화수·하샤드 수 정의를 한 규칙에 넣었더니 약수의 합 자리에 자릿수 합을 썼다.
- **관계없는 규칙도 적용한다.** "같은 형태로 반환하라"를 보고 불리언을 튜플로 감쌌다.
- 반대로 **개념 하나만 담은 규칙이 혼자 주어졌을 때는 정확히 따랐다**(별 수, 혼합 자료형).

이 결과는 LEAP의 공개 모델 실험, IFScale, SkillsBench의 "간결한 스킬이 낫다"와 같은 방향이다.

### 4.5 2차 규칙: 조용히 있다가 필요할 때만

교사는 위 성적과 남은 오답을 보고 규칙 은행을 갱신했다.

- 항상 발동하거나 넓게 발동하는 행동 규칙 8개를 모두 퇴출했다.
- 묶음 지식 규칙을 개념 하나당 규칙 하나로 쪼개고 발동 조건을 좁혔다(예: "hexagonal number"에만 육각수 공식).
- 과제당 보여 주는 규칙을 최대 2개로 제한했다.

결과적으로 유효 규칙 62개 가운데 대부분은 한 문장짜리 정의다. 학습 분할 182문제 중 44문제, 검증 분할 45문제 중 8문제에서만 규칙이 하나 이상 발동하고, 나머지 과제의 프롬프트는 기준선과 같다.

지식 규칙에는 출처를 표시했다. `train_failure`는 학습 분할 실패에 실제로 나온 개념이고, `category`는 교사가 같은 범주(다각수, 이름 붙은 수열, 입체·평면 도형 공식)를 자기 지식으로 채운 것이다. 교사와 학생 모두 공개 벤치마크인 MBPP를 사전학습에서 봤을 수 있으므로, `category` 규칙이 시험 분할에서 낸 효과는 일반화의 증거가 아니라 **낙관적 상한**으로 읽어야 한다.

### 4.6 실행형 규칙

**코드 수정 2종(모델 호출 0회).** 예시가 부르는 함수 이름이 답에 없으면 답이 정의한 함수에 별칭을 달고, 쓰였지만 import되지 않은 표준 라이브러리 이름에 import를 붙인다. 기준선 답안 378개 중 6개가 바뀌었다. 학습 분할에서 1문제가 추가로 풀렸고(원래 테스트 기준 2문제), 깨진 문제는 없었다. 이름이 틀린 답의 절반은 논리도 틀려 있어 이득이 작다.

**탐침 검사기.** 보이는 예시의 인자를 빈 값·음수·0·실수·큰 값 등으로 바꿔 답안을 실행하고 예외나 시간 초과를 본다. 정답표가 없으므로 틀린 값은 알 수 없다. 예시를 통과한 학습 분할 답안 131개 중 숨은 테스트 실패는 16개였는데, 탐침이 하나라도 울린 37개 가운데 실제 실패는 7개(정밀도 19%)였다. 계열별 정밀도도 빈 값 18%, 실수 28%, 음수 33%로, 미리 정한 기준 50%에 못 미쳐 **쓰지 않기로 했다**. 올바른 답도 유효하지 않은 입력에서는 예외를 내기 때문이다.

### 4.7 시험 분할: 읽히는 규칙과 수리 루프는 통하지 않았다

잠가 둔 시험 분할 151문제에서 한 번씩 평가했다. "고침/깨뜨림"은 기준선과 같은 문제끼리 비교한 것이고 p는 정확 McNemar 검정이다.

| 조건 | 원래 테스트 통과 | 숨은 테스트까지 해결 | 고침 / 깨뜨림 | 평균 모델 호출 | 평균 생성 토큰 |
|---|---|---|---|---|---|
| `base` 규칙 없음 | 105 (69.5%) | 89 (58.9%) | — | 1.00 | 93 |
| `base+autofix` 코드 수정 2종 | 106 (70.2%) | 89 (58.9%) | 0 / 0 | 1.00 | 93 |
| `advice` 일반 조언 10줄 | 112 (74.2%) | 93 (61.6%) | 9 / 5 (p=0.424) | 1.00 | 117 |
| `rules` 교사 규칙(2차) | 105 (69.5%) | 89 (58.9%) | 3 / 3 (p=1.000) | 1.00 | 98 |
| `verify` 검증·수리 루프 | 106 (70.2%) | 89 (58.9%) | 0 / 0 | 1.45 | 151 |

- **수리 루프.** 첫 답이 보이는 예시를 틀린 35문제에 두 번까지 고칠 기회를 줬다. 예시를 통과하게 된 것은 2문제이고 숨은 테스트까지 통과한 것은 없다. 호출은 1.45배가 됐다. 틀린 값을 낸 답은 오류 내용을 받아도 같은 답을 되풀이했다.
- **교사 규칙(2차).** 개발 분할에서는 규칙이 발동한 과제에서 학습 16 → 30문제, 검증 4 → 7문제였다. 시험 분할에서는 발동한 29개 과제에서 3문제를 고치고 3문제를 깨뜨렸다. 개발 분할의 이득은 대부분 학습 분할 실패에서 직접 만든 규칙이 같은 과제를 고친 것이었고, 시험 분할에서는 그런 과제가 거의 없었다.
- **일반 조언.** 실패를 보기 전에 써 둔 조언 10줄이 4문제를 더 풀었다. 9문제를 고치고 5문제를 깨뜨린 결과라 유의하지 않다. 교사 규칙이 일반 조언을 이기지 못했다는 점은 그대로 적어 둔다.
- **디코딩 잡음.** 같은 프롬프트를 두 번의 실행에서 풀게 했을 때 생성 텍스트는 151문제 중 16문제에서 달랐고 채점 결과는 한 문제도 달라지지 않았다.

정리하면 4.3절의 분류가 예고한 대로다. 이 학생에게는 읽을 것을 더 주는 방식이 통하지 않는다.

## 5. 막힌 지점과 새 개념: 규칙은 지시가 아니라 가설이다

### 5.1 무엇이 막혔나

교사의 지식을 학생에게 건네는 통로가 둘 다 막혔다.

| 통로 | 방식 | 측정 결과 |
|---|---|---|
| 지시 | 규칙을 프롬프트에 넣고 따르게 한다 | 학습 분할 115 → 107문제. 규칙이 늘수록 악화 |
| 피드백 | 예시를 틀리면 오류를 알려 주고 고치게 한다 | 시험 분할에서 예시를 틀린 첫 답 35개 중 두 번의 수리 뒤 예시를 통과한 것은 2개, 숨은 테스트까지 통과한 것은 0개 |

두 통로는 같은 것을 요구한다. **약한 모델이 글을 읽고 그 뜻대로 행동하는 것**이다. 1.5B 학생은 그것을 하지 못한다. 규칙 속 예시 코드는 그대로 베끼고(`return []`), 자기가 쓴 틀린 답이 대화에 남아 있으면 그 답을 되풀이한다. 규칙을 더 잘 쓰거나 더 많이 쓰는 것으로는 풀리지 않는다.

### 5.2 XOR에 빗대어

단층 퍼셉트론은 입력의 가중합 하나로 답을 낸다. XOR은 가중치를 어떻게 잡아도 풀 수 없고, 입력을 더 넣어도 마찬가지다. 풀린 것은 구조가 바뀌었을 때다. 중간 값을 따로 계산하는 은닉 단위를 두고, 출력의 오차를 그 단위들에게 되돌려 각자를 고치는 규칙(역전파)을 만든 것이다.

여기서 막힌 구조도 같은 모양이다.

| | 퍼셉트론 → 다층 신경망 | 프롬프트 규칙 → 분기·역추론 |
|---|---|---|
| 막힌 구조 | 입력의 가중합을 한 번에 출력으로 | 조언을 한 프롬프트에 쌓아 한 번에 답으로 |
| 못 푸는 이유 | 표현할 수 없는 함수가 있다 | 학생이 조언을 조합해 적용하지 못한다. 조언끼리 간섭한다 |
| 추가한 층 | 은닉 단위: 중간 값을 각자 계산 | 가지(branch): 규칙 하나만 쓴 답, 규칙 없는 답, 연산 규칙을 합성한 프로그램을 각자 만든다 |
| 출력 결정 | 은닉 단위의 결합 | **실행**: 보이는 예시를 재현하는 가지만 통과한다 |
| 오차의 역방향 흐름 | 출력 오차를 은닉 가중치로 | 기대 출력에서 거꾸로 연산을 찾는 탐색(예시 역추론), 개발 분할 결과를 규칙의 유지·퇴출로 되돌리기 |

비유는 구조에 대한 것이다. 여기에는 미분도 경사하강도 없다. 이산적인 탐색과 선택이다.

### 5.3 개념

> **규칙은 모델이 따라야 할 지시가 아니라, 실행해서 확인할 가설이다. 확인된 가설만 답이 된다.**

이 한 문장에서 세 가지 설계가 나온다.

**① 분기-선택.** 규칙을 한 프롬프트에 모아 "모두 지켜라"라고 하지 않는다. 규칙마다 따로 답을 만들고, 규칙 없이 만든 답도 하나의 가지로 둔다. 그중 보이는 예시를 재현하는 첫 답을 고른다. 규칙이 답을 망쳐도 그 가지가 떨어질 뿐이고, 규칙이 답을 고쳤다면 그 가지가 뽑힌다. 어느 가지도 통과하지 못하면 첫 답을 그대로 둔다. 따라서 **가지는 이미 틀린 것으로 확인된 답만 대체한다.**

**② 예시 역추론.** 학생이 낸 답이 모두 예시와 어긋나면 모델을 더 부르지 않는다. 예시의 입력에서 기대 출력으로 가는 계산을 **출력 쪽에서 거꾸로** 찾는다. 약 330개의 작은 연산(정렬, 열별 합, 원소별 AND, 길이 필터, 부분 문자열 위치, …)을 두 단계까지 조합해 예시의 기대값과 같은 값을 내는 식을 열거하고, 과제 설명이 그 연산을 이름으로 부르는 식을 앞에 세운다. 찾은 식이 곧 답 코드다. 4코어 CPU에서 과제당 0.01–0.1초가 걸리고 모델 호출은 0회다.

**③ 지식의 실행 형태.** 1차·2차에서 프롬프트에 넣던 공식·수열 정의를 실행 가능한 연산으로 옮겼다(100개). 과제 설명이 그 개념을 부를 때만 후보가 되고, 예시를 재현해야만 채택된다. "육각수"라는 말이 있어도 `n(2n−1)`이 예시 값을 내지 않으면 쓰이지 않는다. 학생이 공식을 올바르게 적용하는지에 더는 의존하지 않는다.

교사의 일도 바뀐다. 실패 사례를 보고 **지침을 쓰는 대신 연산을 추가한다.** 연산은 실행되므로 학생의 순응 여부와 무관하고, 예시가 걸러 주므로 잘못 추가된 연산이 답을 오염시키기 어렵다. "새 규칙을 계속 추가해야 한다"는 규칙 기반의 약점은 그대로 남지만, 추가한 규칙이 해를 끼치는 경로가 막힌다.

### 5.4 이 개념이 풀지 못하는 것

- **예시가 없으면 아무것도 못 한다.** 선택도 역추론도 예시 실행에 기대고 있다.
- **불리언을 돌려주는 과제.** 예시 하나가 1비트라 역추론할 정보가 없다. 틀린 답도 절반은 예시를 통과한다.
- **연산 두 단계로 표현되지 않는 과제.** 동적 계획법, 재귀 구조, 여러 단계의 수치 계산은 탐색 범위 밖이다.
- **예시는 통과하지만 숨은 입력에서 틀리는 답.** 이 경우 어떤 가지도 작동하지 않는다. 학생의 답이 예시를 통과하면 그대로 채택하기 때문이다.
- **우연의 일치.** 예시 하나로는 프로그램이 정해지지 않는다. 기대값이 작은 정수면 여러 식이 우연히 맞는다.

## 6. 새 개념의 결과

### 6.1 개발 분할

| | 학습 182문제 | 검증 45문제 |
|---|---|---|
| 기준선 | 115 (63.2%) | 24 (53.3%) |
| 기준선 + 예시 역추론 | 142 (78.0%) | 28 (62.2%) |
| 분기-선택(규칙 답 → 규칙 없는 답 → 역추론) | 146 (80.2%) | 29 (64.4%) |

학습 분할은 교사가 규칙과 연산을 만들 때 본 데이터라 낙관적인 수치다. 검증 분할은 연산을 만드는 동안 한 번도 보지 않았다. 표본이 45문제라 한 문제가 2.2%p다.

역추론이 찾은 프로그램은 "확신" 표시를 달고 나온다(기대값이 충분히 구체적이거나, 식의 모든 연산을 과제 설명이 이름으로 부르는 경우). 학습 분할 전체에서 확신 표시가 붙은 프로그램의 80%가 숨은 테스트를 통과했고, 붙지 않은 프로그램은 거의 통과하지 못했다. 다만 실제 파이프라인에서는 이 표시를 쓰지 않는다. 역추론은 학생의 답이 이미 예시를 틀린 과제에만 쓰이므로, 틀린 프로그램을 내도 잃을 것이 없기 때문이다.

연산별 신뢰도를 개발 결과에서 학습하는 장치도 만들어 봤다. 학습 분할에서 예시를 재현한 프로그램 526개를 숨은 테스트로 채점해, 일반화에 성공한 프로그램에 든 연산의 가중치를 올리고 우연히 맞은 프로그램에 든 연산의 가중치를 내렸다. 검증 분할의 결과는 달라지지 않았다. 그래서 최종 설정에는 넣지 않았고 가중치는 기록으로만 남겼다(`reports/rule_pilot/operator_weights_train.json`).

### 6.2 시험 분할

규칙 은행과 연산 라이브러리를 동결한 뒤 한 번 평가했다.

| 조건 | 원래 테스트 통과 | 숨은 테스트까지 해결 | 고침 / 깨뜨림 | 평균 모델 호출 | 평균 생성 토큰 |
|---|---|---|---|---|---|
| `base` 규칙 없음 | 105 (69.5%) | 89 (58.9%) | — | 1.00 | 93 |
| `infer` 기준선 + 예시 역추론 | 114 (75.5%) | 96 (63.6%) | 7 / 0 (p=0.016) | 1.00 | 93 |
| `branch` 분기-선택 | 116 (76.8%) | 97 (64.2%) | 8 / 0 (p=0.008) | 1.06 | 104 |
| `branch` 실제 파이프라인 실행 | 116 (76.8%) | 97 (64.2%) | 8 / 0 (p=0.008) | 1.06 | 106 |

- 분기-선택은 8문제를 고치고 한 문제도 깨뜨리지 않았다. 해결률은 58.9% → 64.2%(95% 신뢰구간 56.3–71.4%)다. 표본이 작아 구간이 넓지만, 같은 문제끼리의 비교에서는 유의하다(p=0.008).
- 실제 파이프라인을 처음부터 끝까지 돌린 결과와, 이미 있는 실행 결과를 조합해 계산한 결과가 151문제 전부에서 일치했다.
- 모델 호출은 과제당 평균 1.06회다. 규칙 답이 예시를 틀렸을 때만 한 번 더 부르고, 역추론은 모델을 부르지 않는다.

어느 가지가 최종 답이 됐는가(시험 분할):

| 최종 답이 된 가지 | 과제 수 | 보이는 예시 통과 | 숨은 테스트까지 해결 | 고침 | 깨뜨림 |
|---|---|---|---|---|---|
| 첫 답 (규칙이 발동했으면 규칙을 읽힌 답) | 129 | 113 | 89 | 3 | 0 |
| 규칙 없는 답으로 물러남 | 6 | 6 | 3 | 0 | 0 |
| 예시 역추론이 찾은 프로그램 | 16 | 16 | 5 | 5 | 0 |

읽는 법:

- **규칙의 손해를 선택이 막았다.** 규칙을 읽힌 답만 쓰면 3문제를 고치고 3문제를 깨뜨린다(4.7절). 분기-선택에서는 규칙 답이 예시를 틀린 과제에서 규칙 없는 답으로 물러섰고, 깨뜨린 문제가 0이 됐다.
- **역추론의 정밀도는 개발 분할보다 낮았다.** 예시를 재현하는 프로그램을 찾은 과제 가운데 숨은 테스트까지 통과한 비율이 학습 분할 64%, 시험 분할 31%(16개 중 5개)였다. 예시 하나로는 프로그램이 정해지지 않는다는 한계가 그대로 드러난다. 그래도 이미 틀린 답만 대체하므로 손해는 없다.
- **지식 규칙의 출처.** 규칙 가지가 고친 문제 가운데 학습 분할 실패에서 나온 개념의 규칙이 1문제, 교사가 범주를 채워 넣은 규칙이 2문제다. 뒤쪽은 교사의 사전지식에서 온 것이라 일반화의 증거로 읽으면 안 된다.

### 6.3 모델 없이 규칙 엔진만으로

학생 모델을 완전히 빼고 예시 역추론만 돌렸다.

| 분할 | 과제 수 | 프로그램을 찾음 | 숨은 테스트까지 해결 |
|---|---|---|---|
| 학습 | 182 | 118 | 80 (44.0%) |
| 검증 | 45 | 28 | 16 (35.6%) |
| 시험 | 151 | 107 | 57 (37.7%) |

신경망이 하나도 없는 규칙 엔진이 과제당 0.1초 안에 낸 결과다. 시험 분할의 37.7%는 0.5B 학생 단독(37.1%)과 같은 수준이다. 다만 푸는 문제가 다르다. 엔진은 연산 두 단계로 표현되는 과제만 풀고, 예시가 불리언이면 손을 대지 못한다. 그래서 둘을 합치면 53.0%가 된다(6.4절).

### 6.4 다른 크기의 학생

규칙 은행과 연산 라이브러리는 1.5B 학생의 실패에서 만든 것 그대로 두고 학생만 바꿨다.

| 학생 (4비트 양자화) | 파일 | 생성 속도 | 규칙 없음 | 분기-선택 | 고침 / 깨뜨림 | 과제당 모델 시간 |
|---|---|---|---|---|---|---|
| Qwen2.5-Coder-0.5B | 0.49GB | 45토큰/초 | 56 (37.1%) | 80 (53.0%) | 24 / 0 | 2.89초 → 3.16초 |
| Qwen2.5-Coder-1.5B | 1.1GB | 17.5토큰/초 | 89 (58.9%) | 97 (64.2%) | 8 / 0 | 5.24초 → 6.93초 |

학생이 약할수록 규칙 엔진이 메우는 몫이 크다. 0.5B 학생에 엔진을 붙인 결과(53.0%)는 엔진 없는 1.5B 학생(58.9%)에 5.9%p 차이까지 다가가는데, 모델 파일은 절반 이하이고 과제당 시간은 0.6배다. 3B와 7B 학생은 시간 제약으로 측정하지 못했다. 공개 수치(전체 378문제, 전정밀도)는 3B 62.4%, 7B 71.7%다.

## 7. 판단

**주장 A — 생성형 모델이 규칙을 쓰고 갱신할 수 있는가: 그렇다. 단, 쓰는 것과 쓸 만한 것은 다르다.**
교사는 실패 67건을 읽고 원인을 붙이고 규칙을 썼다. 그런데 처음 쓴 규칙 27개는 합쳐서 해로웠다. 쓸 만한 규칙 은행이 된 것은 규칙별 성적을 측정하고 해로운 것을 퇴출한 뒤다. 생성형 모델은 규칙 **작성** 비용을 없애지만 규칙 **검증** 비용은 없애지 못한다. 병목이 쓰기에서 고르기로 옮겨 간다.

**주장 B — 규칙이 작은 모델의 코딩 능력을 올리는가: 규칙의 형태에 달렸다.**

| 규칙이 전달되는 형태 | 시험 분할 결과(151문제, 기준 89) |
|---|---|
| 모델이 읽는 일반 조언 | 93 (고침 9, 깨뜨림 5; 유의하지 않음) |
| 모델이 읽는 교사 규칙(2차, 좁은 발동) | 89 (고침 3, 깨뜨림 3) |
| 모델이 읽는 오류 피드백(수리 루프) | 89 (고침 0) |
| 모델 없이 실행되는 코드 수정 | 89 (고침 0) |
| **실행으로 검증되는 가설(분기-선택 + 예시 역추론)** | **97 (고침 8, 깨뜨림 0)** |

능력은 "모델이 읽는 글"로는 거의 옮겨지지 않았고, "실행해서 확인하는 규칙"으로는 옮겨졌다. 증류의 목적지가 가중치도 프롬프트도 아닌 **실행 가능한 규칙 + 검증**일 때 CPU의 작은 모델에 효과가 있었다.

**주장 C — 모든 코딩 기능에서 최상위 수준: 성립하지 않는다.**
가장 쉬운 축인 단일 함수 작성에서도 1.5B 학생과 규칙 엔진의 합은 64.2%로, 공개된 7B 수치(71.7%)와 최상위 모델(75% 이상)에 못 미친다. 이득은 보이는 예시가 있고, 답이 연산 두 단계로 표현되는 과제에 한정된다. 저장소 단위 작업처럼 열린 과제에서의 격차(3.3절)는 이 구조로 좁힐 방법이 없다.

정리하면, **"규칙으로 CPU 모델을 전 기능 최상위로"는 불가능하고, "검증 가능한 좁은 기능에서 규칙 엔진이 작은 모델의 실패를 메운다"는 가능하며 측정됐다.**

## 8. 제안 구조와 다음 단계

측정에서 살아남은 것만으로 구성한 구조다.

```
[오프라인 · 교사 (큰 생성형 모델, 가끔 실행)]
  개발 분할 실패(오답 은행) ─▶ 원인 분류 ─▶ ① 연산 추가 (실행 규칙)
        ▲                                    ② 개념 하나짜리 지식 규칙 (좁은 발동 조건)
        │                                         │
        │                      잠근 분할에서 효과 측정 → 해로운 것 퇴출
        │                                         ▼
        └────────── 새 실패 ◀──── 버전이 붙은 규칙 은행·연산 라이브러리

[온라인 · CPU]
  요청 + 예시 ─▶ 작은 LLM (발동한 규칙이 있으면 최대 2개를 읽힌 답)
                    │ 예시 재현?  ── 예 ─▶ 채택
                    ▼ 아니오
                 규칙 없는 답      ── 예 ─▶ 채택
                    ▼ 아니오
                 예시 역추론 (모델 호출 0회)  ── 찾음 ─▶ 채택
                    ▼ 못 찾음
                 첫 답을 "검증 실패" 표시와 함께 반환, 오답 은행에 기록
```

설계 원칙:

1. **규칙은 가능한 한 실행 가능한 형태로 만든다.** 읽히는 규칙은 모델이 따라야 효과가 나고, 따르지 않거나 잘못 따르면 해가 된다. 실행되는 규칙은 모델의 순응과 무관하다.
2. **규칙을 쌓지 말고 가지로 나눈다.** 한 프롬프트에 규칙이 늘수록 나빠졌다. 가지마다 따로 답을 만들고 실행으로 고른다.
3. **이미 틀린 답만 대체한다.** 예시를 통과한 답은 건드리지 않는다. 그래서 어떤 가지도 손해를 만들지 않았다.
4. **효과가 측정된 규칙만 남긴다.** 교사가 쓴 규칙도 가설이다. 잠근 분할 없이 규칙을 늘리면 본 사례에만 맞는 규칙이 쌓인다.
5. **검증기가 시스템의 상한이다.** 검증할 수 없는 기능(설계 조언, 열린 리팩터링)에는 이 구조를 쓰지 않는다.

기능별 현실적 목표:

| 코딩 기능 | CPU에서의 주 수단 | 최상위 수준 도달 가능성 |
|---|---|---|
| 포맷·린트·임포트 정리·알려진 버그 패턴 탐지 | 규칙 엔진(LLM 불필요) | 가능. 이미 규칙 기반이 표준이다 |
| 예시가 있는 단순 함수 작성 | 작은 모델 + 분기-선택 + 예시 역추론 | 부분적. 이 문서의 측정 범위 |
| 실패 테스트가 있는 버그 수정 | 작은 모델 + 테스트를 검증기로 | 미측정. 수리 루프는 통하지 않았으므로 재생성과 선택으로 접근해야 한다 |
| 줄·블록 자동완성 | 1.5–3B 모델 | 줄 단위는 근접, 여러 줄은 미달 |
| 저장소 단위 이슈 해결·다단계 작업 | (작은 모델로는 부족) | 현재 불가. 대규모로 증류한 7B도 최상위의 절반 수준이다 |
| 설계·아키텍처 판단 | (검증기 없음) | 불가 |

### 다음 단계


효과가 측정된 것부터, 비용이 작은 순서로 적는다.

1. **연산 라이브러리를 교사가 계속 키운다.** 역추론이 프로그램을 찾지 못했거나 찾은 프로그램이 숨은 테스트에서 틀린 개발 분할 과제를 교사에게 주고 연산을 추가하게 한다. 이번에는 한 번만 돌렸다. 추가한 연산은 잠근 분할에서 정밀도를 확인한 뒤에만 유지한다.
2. **예시를 늘린다.** 역추론의 오답은 대부분 예시 하나가 프로그램을 정하지 못해서 생긴다. 예시가 두세 개면 우연의 일치가 줄 것으로 예상한다(측정하지 않았다). 사용자에게 예시를 하나 더 요청하거나, 학생 모델이 만든 추가 예시를 사람이 확인하는 흐름을 붙인다.
3. **학생을 한 단계 키운다.** 규칙 엔진은 학생 크기와 무관하게 붙는다(0.5B 학생은 37.1% → 53.0%, 1.5B 학생은 58.9% → 64.2%). CPU에서 견딜 수 있는 가장 큰 모델을 쓰고 엔진을 얹는 것이 현재 가장 싼 향상이다.
4. **기능을 하나씩 넓힌다.** 다음 후보는 검증기가 분명한 기능이다: 실패 테스트가 있는 버그 수정(테스트가 검증기), 타입 오류 수정(타입 검사기가 검증기). 검증기가 없는 기능에는 이 구조를 쓰지 않는다.
5. **가중치 증류와 비교한다.** 오답 은행은 그대로 미세조정 데이터가 된다. GPU가 생기면 같은 데이터로 LoRA를 학습해 규칙 엔진과 비교하고, 둘을 겹쳐 본다.

## 9. 한계와 확인하지 못한 것

- **과제 한 종류, 학생 한 계열.** 단일 함수 Python 과제(MBPP+)만 측정했다. 자동완성, 리팩터링, 테스트 생성, 저장소 단위 작업은 측정하지 않았고 3절의 문헌 수치에 의존한다. 학생은 Qwen2.5-Coder 계열뿐이다.
- **표본이 작다.** 시험 분할은 151문제라 한 문제가 0.66%p다. 5%p 안팎의 차이는 신뢰구간 안에 들어온다.
- **교사와 학생 모두 벤치마크를 봤을 수 있다.** MBPP는 공개 데이터라 사전학습에 포함됐을 가능성이 높다. 분할은 "시험 실패를 보고 규칙을 고치는 것"을 막을 뿐, 교사가 원래 알고 있던 출제 경향까지 막지 못한다. 그래서 지식 규칙의 출처를 표시하고 결과를 따로 보고했다.
- **디코딩 잡음.** temperature 0에 시드를 고정했지만, llama.cpp 서버의 프롬프트 캐시 상태에 따라 같은 프롬프트의 생성 텍스트가 151문제 중 16문제에서 달라졌다. 채점 결과가 달라진 문제는 없었다. 실행 간 비교에는 이 잡음이 섞일 수 있다.
- **예시가 있어야 한다.** 분기-선택도 예시 역추론도 프롬프트의 예시 `assert` 하나를 실행하는 데 기대고 있다. 예시나 테스트가 없는 요청에는 이 이득이 없다.
- **연산과 규칙은 학습 분할을 보며 만들었다.** 학습 분할 수치(80.2%)는 낙관적이다. 일반화의 추정치는 시험 분할 수치다. 지식 규칙과 지식 연산 가운데 교사가 범주를 채워 넣은 것은 교사의 사전지식에서 왔다.
- **역추론의 정밀도.** 예시를 재현하는 프로그램이 숨은 테스트까지 통과한 비율은 시험 분할에서 31%였다. 예시를 통과했다는 표시를 정답 보증으로 쓰면 안 된다.
- **더 큰 학생은 측정하지 않았다.** 3B, 7B 학생에 같은 엔진을 붙였을 때의 이득은 모른다. 학생이 강할수록 엔진이 메울 몫은 줄 것이다.
- **교사 한 명, 갱신 두 번.** 규칙은 이 세션의 교사 모델이 두 차례 쓴 것이다. 다른 교사나 더 많은 갱신 회차에서 결과가 달라질 수 있다. 자동 API 파이프라인이 아니라 대화형 세션에서 교사 역할을 수행했다.
- **가중치 증류와 비교하지 않았다.** 같은 실패 데이터로 LoRA 미세조정을 했을 때의 효과는 이 환경(GPU 없음)에서 측정하지 못했다.
- **실행 중 사고.** 다른 모델을 같은 CPU에 동시에 띄웠다가 몇 문제의 소요 시간이 부풀었다. 답안에는 영향이 없고, 시간 통계는 중앙값을 함께 적었다.

## 10. 재현

```bash
python -m venv .venv && . .venv/bin/activate
pip install --no-deps evalplus==0.3.1 && pip install -r requirements-rule-pilot.txt

python scripts/rule_pilot_install.py --models coder-1.5b     # 런타임·데이터셋·모델을 받고 SHA-256 대조
bash scripts/rule_pilot_serve.sh coder-1.5b 8081 &           # 127.0.0.1에서만 수신

# 기준선과 교사용 오답 은행
python scripts/rule_pilot.py generate --name s15-base --condition base --split all
python scripts/rule_pilot.py score --name s15-base --diagnose
python scripts/rule_pilot.py export-failures --name s15-base \
    --output outputs/rule_pilot/teacher/round1_train_failures.json

# 규칙별 효과 측정 (무작위 부분집합 + 라쏘)
python scripts/rule_pilot.py generate --name s15-attr1 --condition rules --split train --random-subsets
python scripts/rule_pilot.py score --name s15-attr1 --reuse s15-base --diagnose
python scripts/rule_pilot.py attribute --name s15-attr1 --baseline s15-base --splits train \
    --output reports/rule_pilot/attribution_round1.json

# 최종 파이프라인: 규칙 답 → 규칙 없는 답 → 예시 역추론
python scripts/rule_pilot.py generate --name s15-branch-live --condition branch --split test --max-rules 2
python scripts/rule_pilot.py score --name s15-branch-live --reuse s15-base
python scripts/rule_pilot.py summary --names s15-base s15-branch-live --split test
python scripts/rule_pilot.py breakdown --name s15-branch-live --baseline s15-base --split test

# 모델 없이 규칙 엔진만
python scripts/rule_pilot.py select --candidates s15-base --output-name engine-only --engine-only
python scripts/rule_pilot.py score --name engine-only

python -m unittest discover -s tests -v
```

모델 가중치, 런타임, 데이터셋 원본, 생성 결과(`outputs/`)는 Git에서 제외한다. 규칙 은행, 분할, 채점 요약은 저장소에 있다. 서버는 한 번에 하나만 띄운다. 4코어에서 두 서버를 동시에 돌리면 둘 다 수십 배 느려진다.
