# SeedLM: 규칙 엔진이 가르친, 처음부터 만든 소형 언어 모델

작성일: 2026-11-18. [규칙 증류 가능성 검토](rule_distillation_feasibility.md)의 후속이다. 사전학습 가중치도 외부 말뭉치도 쓰지 않고 트랜스포머를 처음부터 학습시켰다. 측정은 모두 이 저장소 환경(CPU 4코어, GPU 없음)에서 했다.

## 요약

1. **처음부터 만들었다.** 사전학습 가중치도 외부 말뭉치도 없이 142만 파라미터 트랜스포머를 CPU 4코어에서 20분 학습했다. 학습 데이터는 규칙 엔진의 연산 라이브러리가 스스로 만든다.
2. **직교 초기화와 직교화 갱신(Muon)은 이 규모에서도 통했다.** 같은 6분 학습에서 손실이 1.72 → 1.56 → 1.22로 내려갔다. 시드 하나, 학습률 미조정이라 크기는 대략적이다.
3. **모델은 규칙 라이브러리를 배웠다.** 학습에 쓰지 않은 합성 예시에서 첫 제안이 예시를 재현하는 비율이 57.0%, 빔 8개 안에 재현하는 프로그램이 있는 비율이 81.3%다. 혼자서 MBPP+ 시험 분할 151문제 중 43문제(28.5%)를 푼다.
4. **실제 과제에서는 규칙 엔진의 전수 탐색을 넘지 못했다.** 같은 예시에서 전수 탐색은 55문제(36.4%)를 풀고, 탐색이 못 찾은 과제를 모델이 푼 경우가 없다. 파이프라인의 가지로 붙여도 수치가 달라지지 않는다.
5. **모델이 유리한 곳은 전수 탐색이 닿지 않는 깊이다.** 연산 3개짜리 합성 프로그램 100개에서 모델은 65개, 전수 탐색은 55개를 찾았고 모델만 찾은 것이 15개다. 연산 2개짜리에서는 탐색이 낫다(91 대 80).
6. **새 규칙을 추가할 때 기존 규칙을 지킨 것은 직교 방향이 아니라 데이터였다.** 새 규칙의 프로그램만 보여 주면 기존 규칙 예시의 첫 제안 재현율이 54.0% → 25.3%로 무너진다. 기존 분포의 프로그램을 절반 섞으면 49.3%다(추가 전과의 차이는 표본 오차 안). 새 연산의 행만 학습해도(파라미터의 0.7%) 같은 결과가 나온다. 그 행을 "기존 행이 덜 쓰는 방향"에서 시작하는 것은 무작위 시작과 차이가 없었다.
7. **범용 코딩 LLM이 아니다.** 자연어를 이해하지 못하고, 교사가 만든 연산 328개의 조합만 출력한다.

## 1. 무엇이고 무엇이 아닌가

- **처음부터 만들었다.** 구조, 토큰 배치, 학습 루프, 옵티마이저, 빔 탐색을 직접 작성했다. 학습 데이터는 전부 규칙 엔진의 연산 라이브러리가 만든다. 연산 프로그램 하나를 뽑아 무작위 인자에 실행하고, 모델에게 "이 입력과 출력을 보고 프로그램을 맞혀라"를 시킨다. 정답이 실행으로 만들어지므로 라벨 오류가 없고 데이터가 떨어지지 않는다.
- **하는 일은 하나다.** 예시의 입력과 기대 출력, 그리고 과제 설명이 이름을 부른 연산 목록을 보고 연산 프로그램을 제안한다. 제안은 실행해서 예시를 재현하는지 확인한 뒤에만 쓰인다. 신경망이 프로그램을 제안하고 실행이 걸러 내는 구도는 DeepCoder(2017) 이래의 방식이고 새로운 것이 아니다.
- **범용 코딩 LLM이 아니다.** 자연어를 이해하지 못하고 Python 코드를 자유롭게 쓰지 못한다. 파라미터는 약 142만 개다.

### 왜 범용 코딩 LLM을 처음부터 만들지 않았나

이 환경에서 불가능하기 때문이다. 근거는 규모다.

| | 이 환경에서 측정 | 범용 소형 코딩 모델 |
|---|---|---|
| 파라미터 | 142만 | 5억(Qwen2.5-Coder-0.5B) 이상 |
| 학습량 | 41.1만 시퀀스(약 2,150만 토큰, 그중 학습 대상인 프로그램 토큰은 약 160만 개), 20분 | 5.5조 토큰(Qwen2.5-Coder 기술 보고서) |
| 장비 | CPU 4코어 | GPU 클러스터(규모는 공개되지 않았다) |

공개된 선례도 같은 방향이다. TinyStories는 100만~3,500만 파라미터 모델을 V100 한 장으로 최대 30시간 학습해 짧은 동화를 쓰게 했지만 100만 파라미터 모델은 "사실 질문에 하나도 답하지 못한다"고 보고했다. nanochat의 CPU 경로(M3 Max에서 약 30분)는 문서에 "이 방식으로는 좋은 결과를 얻을 수 없다"고 적혀 있다. 그래서 처음부터 만드는 모델은 **좁지만 실제로 쓰이는 일**에 맞췄다.

## 2. 설계: 직교성을 어디에 넣었나

| 설계 | 내용 | 직교성과의 관계 | 근거와 주의 | 이 문서에서 측정한 결과 |
|---|---|---|---|---|
| 회전 위치 임베딩 | 위치를 질의·키 벡터의 회전으로 넣는다 | 회전은 직교 변환이라 벡터 길이를 보존한다. 위치 표를 학습할 필요가 없다 | 현행 소형 모델 레시피의 표준 | 따로 비교하지 않았다 |
| 직교 초기화 + 항등 블록 | 모든 행렬을 직교 행렬로 시작하고, 잔차 흐름에 쓰는 두 사영은 0으로 시작한다 | 신호의 크기를 층마다 보존한다. 각 블록은 처음에 항등 함수다 | 언어 모델에서의 근거는 얇다. 현행 레시피는 직교 초기화를 쓰지 않는다. 그래서 직접 비교했다 | **효과 있음.** 같은 6분 학습에서 손실 1.72 → 1.56 (3절) |
| 규칙마다 직교 방향 | 연산 토큰의 임베딩 행을 서로 직교하게 시작한다(폭이 허락하는 만큼) | 규칙 사이의 간섭을 줄인다 | 연산 328개 > 폭 160이라 완전한 직교는 아니다. 행 사이 코사인 절댓값의 평균이 0.045다(무작위 방향이면 0.063) | 위의 직교 초기화 조건에 묶여 있어 따로 떼어 비교하지 않았다 |
| 직교화 갱신(Muon) | 은닉 행렬을 기울기 방향이 아니라 모멘텀의 직교화(UVᵀ 근사)로 갱신한다 | 갱신의 모든 방향 크기를 비슷하게 맞춘다 | 공식 구현을 그대로 옮겼다. 1억 파라미터 이상에서는 AdamW 대비 1.1~1.4배가 보고됐지만, 수백만 파라미터·CPU·작은 배치에서의 비교는 찾지 못했다 | **효과 있음.** 손실 1.56 → 1.22 (3절) |
| 새 규칙의 직교 추가 | 새 연산의 임베딩·출력 행을 기존 연산 행이 가장 덜 쓰는 방향에서 시작하고, 그 행만 학습한다 | 기존 규칙의 행을 건드리지 않는다 | 연속학습의 직교 부분공간 방법(O-LoRA, 저특이값 방향 미세조정)과 같은 생각이다 | **절반만 통했다.** 새 행만 학습하는 것은 통했지만, 덜 쓰는 방향에서 시작하는 것은 무작위 시작과 차이가 없었다 (5절) |
| 코사인 주의, RMSNorm, ReLU² | 질의·키를 정규화하고, 사전 정규화에 파라미터 없는 RMSNorm, 활성화는 ReLU² | 직교성과 직접 관련은 없다 | 현행 소형 모델 레시피를 따랐다 | 따로 비교하지 않았다 |
| 문법 제약 빔 탐색 | 연산의 인자 수를 세어, 완성될 수 있는 프로그램만 디코딩한다 | — | 규칙(문법)이 모델의 출력을 제한한다 | 따로 비교하지 않았다 |

넣지 않은 것: nGPT식 전면 정규화(재현 연구에서 이득이 원 논문보다 작았고, 이미 쓰는 코사인 주의 대비 1.29배로 보고됐다), 직교 미세조정(OFT 계열, 사전학습 가중치가 있어야 의미가 있다).

토큰 배치는 다음과 같다. 프로그램 부분만 학습 대상이다.

```
BOS  <인자 목록의 바이트>  OUT  <기대값의 바이트>  NAMED  <설명이 부른 연산 토큰들>  PROG  <프로그램(전위 표기)>  EOS
```

## 3. 측정 1: 직교 초기화와 직교화 갱신은 이 규모에서도 통했다

같은 모델(1,418,900 파라미터, 폭 160, 4층), 같은 생성기와 같은 시드로 만든 합성 학습 데이터 15만 개, 같은 배치 크기 64로 **벽시계 6분씩** 학습했다. 학습에 쓰지 않은 합성 예시 300개로 평가했다. 연산 328개를 모두 썼다. 두 초기화 모두 잔차 흐름에 쓰는 사영은 0에서 시작한다. 다른 점은 나머지 행렬을 직교 행렬로 시작하는가이고, 연산 토큰 임베딩 행의 직교 시작도 여기에 포함된다.

| 설정 | 스텝 | 본 시퀀스 | 손실 | 첫 제안이 정답 프로그램과 같음 | 첫 제안이 예시를 재현 | 빔 8개 중 하나가 예시를 재현 |
|---|---|---|---|---|---|---|
| AdamW + 표준 초기화(정규분포 0.02) | 2,023 | 12.9만 | 1.718 | 14.0% | 24.0% | 51.0% |
| AdamW + 직교 초기화 | 2,272 | 14.5만 | 1.558 | 21.7% | 32.3% | 55.0% |
| Muon(은닉 행렬) + 직교 초기화 | 2,001 | 12.8만 | 1.220 | 28.7% | 38.7% | 65.0% |

- **직교 초기화.** 손실이 1.72 → 1.56으로 내려갔다. 첫 실행 중에 다른 명령이 CPU를 써서 본 시퀀스 수가 다르다. 같은 9.5만 시퀀스 시점으로 맞추면 1.80 대 약 1.70이다.
- **직교화 갱신(Muon).** 같은 시점의 손실이 1.34다. 뉴턴-슐츠 반복 때문에 스텝이 약 12% 느리지만(2,001 대 2,272 스텝), 같은 6분에 손실은 1.56 → 1.22, 빔 8개 재현율은 55% → 65%가 됐다.
- **이 표를 어디까지 믿을 수 있나.** 설정마다 시드 하나로 한 번씩 돌렸고 학습률을 조정하지 않았다. AdamW는 2e-3 하나만 써 봤으므로 덜 조정됐을 수 있다. Muon은 공식 기본값(학습률 0.02)에 가중치 감쇠 0.01을 줬다. 작은 배치에서는 가중치 감쇠가 필요하다는 보고를 따랐다. 차이가 커서 방향은 분명하지만 크기는 대략적이다.

## 4. 측정 2: 본 학습

Muon과 직교 초기화로 20분 학습했다. 연산 328개 가운데 30개(일반 연산 17개, 지식 연산 13개)는 일부러 빼고 학습했다. 5절에서 새 규칙으로 추가하기 위해서다. 그래서 아래 수치는 연산 298개짜리 문제에 대한 것이고, 3절의 표(328개)와 곧바로 비교할 수 없다. 시퀀스 하나는 평균 52토큰이고 그중 학습 대상인 프로그램 부분은 평균 4토큰이다.

| | 값 |
|---|---|
| 스텝 / 본 시퀀스 | 6,425 / 41.1만 |
| 합성 데이터 생성 | 104초 (학습용 40만 시퀀스와 평가용 1,000개) |
| 학습에 쓰지 않은 예시 300개의 손실 | 0.836 |
| 첫 제안이 정답 프로그램과 같음 | 43.3% |
| 첫 제안이 예시를 재현 | 57.0% |
| 빔 8개 중 하나가 예시를 재현 | 81.3% |
| 가중치 파일 | 5.7MB (32비트 실수) |
| 제안 한 번(빔 32개, 실행 검증 포함) | 0.3~0.4초 (6.3절) |

학습 곡선(평가 예시 60개 기준이라 거칠다):

| 경과 | 본 시퀀스 | 손실 | 첫 제안이 예시를 재현 | 빔 8개 중 하나가 재현 |
|---|---|---|---|---|
| 5분 | 10.8만 | 1.261 | 41.7% | 66.7% |
| 10분 | 21.6만 | 1.031 | 48.3% | 76.7% |
| 15분 | 31.5만 | 0.896 | 56.7% | 81.7% |
| 끝(300개로 평가) | 41.1만 | 0.836 | 57.0% | 81.3% |

"정답 프로그램과 같음"보다 "예시를 재현"이 높은 것은 같은 출력을 내는 프로그램이 여럿이기 때문이다. 모델이 낸 프로그램이 정답과 달라도 실행해서 같은 값을 내면 쓸 수 있다.

손실은 끝까지 내려가고 있었다(15분 0.896 → 20분 0.836). 더 오래 학습하면 더 오를 여지가 있지만 재지 않았다. 마지막 5분 동안 짧은 점검 명령 두 개가 같은 CPU에서 돌아 스텝 수가 조금 줄었다.

## 5. 측정 3: 새 규칙을 추가해도 기존 규칙이 망가지지 않는가

본 학습에서 뺀 연산 30개를 "새 규칙"으로 추가했다. 두 가지 선택을 조합했다. 어느 가중치를 움직이는가(전부 / 새 연산 토큰의 임베딩·출력 행만), 그리고 어떤 프로그램을 보여 주는가(새 연산이 든 것만 / 그것과 기존 분포에서 뽑은 것을 절반씩). 모두 같은 모델에서 출발해 2.5분씩(947~1,212스텝) 학습했다. 옵티마이저는 AdamW이고 학습률은 1e-3으로 고정했다. 조정하지 않았다. 평가는 예시 150개씩이다(기존 연산만 쓰는 프로그램 / 새 연산이 하나 이상 든 프로그램).

| 움직이는 가중치 | 보여 준 프로그램 | 기존: 손실 | 기존: 첫 제안 재현 | 기존: 빔 8개 재현 | 새 연산: 손실 | 새 연산: 첫 제안 재현 | 새 연산: 빔 8개 재현 |
|---|---|---|---|---|---|---|---|
| (추가 전) | — | 0.84 | 54.0% | 81.3% | 5.35 | 14.7% | 24.0% |
| 전부(142만 개) | 새 연산이 든 것만 | 1.84 | 25.3% | 49.3% | 0.92 | 55.3% | 74.7% |
| 전부(142만 개) | 절반씩 | 0.98 | 48.0% | 74.7% | 0.91 | 50.0% | 73.3% |
| 새 연산의 행만(9,600개), 기존 행이 덜 쓰는 방향에서 시작 | 새 연산이 든 것만 | 1.09 | 38.0% | 73.3% | 0.94 | 48.7% | 74.0% |
| 새 연산의 행만(9,600개), 기존 행이 덜 쓰는 방향에서 시작 | 절반씩 | 0.94 | 49.3% | 77.3% | 0.94 | 48.7% | 74.0% |
| 새 연산의 행만(9,600개), 무작위 방향에서 시작 | 절반씩 | 0.93 | 49.3% | 78.0% | 0.93 | 48.7% | 73.3% |

"추가 전"은 실행마다 다시 쟀다. 다섯 번 가운데 네 번은 표의 값이고, 한 번은 기존 연산의 첫 제안 재현율이 54.7%였다. 평가 예시 하나가 달라진 것이다(7절의 재현성 항목).

읽는 법. 평가 예시가 150개라 비율 하나의 95% 신뢰구간이 ±8%p쯤이다. 그 안의 차이는 구별되지 않는다.

- **전체 미세조정은 2.5분 만에 기존 규칙을 잊었다.** 새 연산이 든 프로그램만 보여 주면 새 연산은 배우지만(14.7% → 55.3%) 기존 연산 예시의 첫 제안 재현율이 54.0% → 25.3%로 떨어진다. 첫 제안이 정답 프로그램과 같은 비율은 40.7% → 4.7%다.
- **새 연산의 행만 학습해도 새 연산을 거의 같은 수준으로 배운다**(48.7%, 빔 8개 74.0%). 움직인 파라미터는 9,600개로 전체의 0.7%다. 본 학습에서 "설명이 부른 연산을 프로그램에 옮겨 쓰는" 일반적인 경로가 이미 만들어졌기 때문이라고 추정한다. 직접 확인하지는 않았다.
- **기존 행을 얼렸는데도 기존 성능이 내려갔다**(54.0% → 38.0%). 기존 연산의 행과 본체는 전혀 바뀌지 않았으므로 덮어쓰기 때문이 아니다. 새 행이 "새 연산이 반드시 들어가는 프로그램"만 보고 학습해, 어떤 입력에서도 자기 확률을 높게 내도록 배운 것이다. 원인은 망각이 아니라 **치우친 데이터가 만든 사전확률**이다.
- **기존 분포의 프로그램을 절반 섞으면 이 문제가 사라진다.** 행만 학습하는 쪽은 기존 49.3% / 새 연산 48.7%, 전체 미세조정은 48.0% / 50.0%로 구별되지 않는다. 둘 다 추가 전(54.0%)보다 5%p쯤 낮은데, 실제 손실인지는 이 표본으로 말할 수 없다.
- **"덜 쓰는 방향에서 시작"은 효과가 없었다.** 무작위 방향에서 시작한 대조군이 기존 49.3% / 새 연산 48.7%로 같았다. 폭 160에 연산이 328개라 "덜 쓰는 방향"도 비어 있지 않고, 1,000스텝 넘게 학습하는 동안 시작 방향의 영향이 지워진 것으로 보인다. 2절의 설계 가운데 이 항목은 근거를 얻지 못했다.

정리하면, 이 모델에서 새 규칙을 추가할 때 기존 규칙을 지킨 것은 직교 방향이 아니라 **기존 분포의 데이터를 섞는 것**이었다. 생성기가 데이터를 얼마든지 만들기 때문에 비용이 없다. 본체를 얼리고 새 행만 학습하는 방법은 같은 결과를 0.7%의 파라미터로 내고, 기존 가중치가 바뀌지 않는다는 것을 구조로 보장한다.

6절에는 "새 행만, 절반씩"으로 만든 모델을 썼다. 고르는 기준은 나머지 결과를 보기 전에 정했다(기존과 새 연산의 첫 제안 재현율 합). 전체 미세조정(절반씩)과 합이 같아서 빔 8개 재현율 합이 높은 쪽을 골랐다.

## 6. 측정 4: 실제 과제에서 보탬이 되는가

### 6.1 예시 하나를 보고 프로그램을 맞히는 능력

규칙 엔진의 전수 탐색(연산 두 단계)과 SeedLM의 제안(빔 32개, 실행으로 검증)을 MBPP+ 과제의 보이는 예시에 각각 돌렸다. 예시가 불리언이거나 집합·근사 비교인 과제는 SeedLM의 대상이 아니다. 시험 분할은 개수만 셌다.

| 5절의 어느 모델인가 | 분할, 과제 수 | 대상 예시 | 전수 탐색: 예시 재현 / 숨은 테스트 통과 | SeedLM: 예시 재현 / 첫 제안이 숨은 테스트 통과 | 탐색이 못 찾은 과제에서 SeedLM: 재현 / 통과 | 탐색과 같은 프로그램 |
|---|---|---|---|---|---|---|
| 새 행만 학습, 새 연산 프로그램만 | 학습 182 | 141 | 112 / 74 | 87 / 57 | 0 / 0 | 61 |
| 새 행만 학습, 새 연산 프로그램만 | 검증 45 | 35 | 26 / 14 | 18 / 8 | 0 / 0 | 9 |
| 새 행만 학습, 새 연산 프로그램만 | 시험 151 | 127 | 104 / 55 | 80 / 40 | 1 / 0 | 52 |
| 새 행만 학습, 절반씩 | 학습 182 | 141 | 112 / 74 | 88 / 60 | 0 / 0 | 67 |
| 새 행만 학습, 절반씩 | 검증 45 | 35 | 26 / 14 | 19 / 9 | 0 / 0 | 10 |
| 새 행만 학습, 절반씩 | 시험 151 | 127 | 104 / 55 | 82 / 43 | 1 / 0 | 57 |

읽는 법. 아래 수치는 5절 끝에서 고른 모델(새 행만 학습, 절반씩)의 것이다.

- **사전학습 가중치가 전혀 없는 모델이 혼자서 과제를 푼다.** SeedLM의 첫 번째 검증된 제안이 숨은 테스트까지 통과한 과제가 학습 분할 60문제(33.0%), 검증 분할 9문제(20.0%), 시험 분할 43문제(28.5%)다. 전수 탐색의 도움 없이 낸 수치다. 참고로 같은 시험 분할에서 Qwen2.5-Coder-0.5B(4비트) 단독은 56문제(37.1%)였다. 다만 SeedLM은 보이는 예시와 교사가 만든 연산 라이브러리가 있어야만 답을 낸다.
- **같은 규칙을 전수 탐색하는 쪽이 더 많이 푼다.** 학습 분할 74문제(40.7%), 검증 분할 14문제(31.1%), 시험 분할 55문제(36.4%)다. [가능성 검토](rule_distillation_feasibility.md) 6.3절의 80 / 16 / 57문제보다 적은 것은 여기서 불리언·집합·근사 비교 예시를 뺐기 때문이다. 모델이 예시를 재현한 과제의 대부분에서 모델의 첫 제안은 탐색이 고른 프로그램과 같았다(시험 분할 57/82).
- **탐색이 못 찾은 과제를 모델이 푼 경우는 없다.** 그런 과제에서 SeedLM이 예시를 재현한 것은 세 분할을 합쳐 1건이고, 숨은 테스트까지 통과한 것은 0건이다.

### 6.2 파이프라인의 마지막 가지로

분기-선택에 네 번째 가지를 달 수 있게 했다(`--seedlm`). 규칙을 읽힌 답, 규칙 없는 답, 전수 탐색이 모두 예시를 재현하지 못한 과제에만 SeedLM의 첫 번째 검증된 제안을 쓴다. 이미 틀린 답만 대체하므로 깨뜨리는 문제는 생길 수 없다.

| 구성 | 분할 | SeedLM 없이 해결 | SeedLM 가지를 더해 해결 | 차이 |
|---|---|---|---|---|
| 규칙 엔진만(사전학습 가중치 없음) | 학습 182문제 | 81 (44.5%) | 81 (44.5%) | +0 |
| 규칙 엔진만(사전학습 가중치 없음) | 검증 45문제 | 16 (35.6%) | 16 (35.6%) | +0 |
| 규칙 엔진만(사전학습 가중치 없음) | 시험 151문제 | 57 (37.7%) | 57 (37.7%) | +0 |
| 1.5B 학생 + 분기-선택 | 학습 182문제 | 146 (80.2%) | 146 (80.2%) | +0 |
| 1.5B 학생 + 분기-선택 | 검증 45문제 | 29 (64.4%) | 29 (64.4%) | +0 |
| 1.5B 학생 + 분기-선택 | 시험 151문제 | 97 (64.2%) | 97 (64.2%) | +0 |
| 0.5B 학생 + 분기-선택 | 시험 151문제 | 80 (53.0%) | 80 (53.0%) | +0 |

해결 문제 수는 어느 구성에서도 달라지지 않았다. SeedLM의 제안이 최종 답이 된 과제는 1.5B와 0.5B 파이프라인에서 0건, 규칙 엔진 단독에서 시험 분할 1건이고 그 1건은 숨은 테스트를 통과하지 못했다. "SeedLM 없이" 열은 연산 하나를 고친 뒤(7절) 다시 계산한 값이다. 규칙 엔진 단독의 학습 분할이 80이 아니라 81인 까닭이다.

### 6.3 그러면 학습한 제안기는 언제 쓸모가 있는가: 프로그램 깊이별 비교

전수 탐색은 연산 두 개까지의 프로그램을 빠짐없이 본다. 그보다 깊은 프로그램은 보지 못한다. 학습한 제안기는 깊이 제한이 없지만 빔에 든 후보만 본다. 학습에 쓰지 않은 합성 예시를 프로그램의 연산 수별로 100개씩 뽑아, 예시를 재현하는 프로그램을 찾는 비율을 쟀다. 두 방법에 같은 힌트(설명이 부른 연산 목록)를 줬다.

| 프로그램의 연산 수 | 전수 탐색이 찾음 | SeedLM(빔 32)이 찾음 | 둘 다 | 탐색만 | SeedLM만 | 둘 다 못 찾음 | 탐색 시간 | SeedLM 시간 |
|---|---|---|---|---|---|---|---|---|
| 1 | 98 | 98 | 97 | 1 | 1 | 1 | 0.05초 | 0.36초 |
| 2 | 91 | 80 | 78 | 13 | 2 | 7 | 0.03초 | 0.33초 |
| 3 | 55 | 65 | 50 | 5 | 15 | 30 | 0.03초 | 0.30초 |

- **연산 1개.** 둘 다 거의 다 찾는다.
- **연산 2개.** 전수 탐색이 낫다(91 대 80, 정확 맥니마 검정 p=0.007). 탐색은 이 깊이를 빠짐없이 보고 모델은 빔 32개만 본다. 탐색이 연산 1~2개짜리에서 놓친 11개 가운데 9개는 힌트가 이름을 부르지 않아 잠겨 있는 지식 연산이 든 프로그램이었다.
- **연산 3개.** 모델이 낫다(65 대 55). 모델만 찾은 예시가 15개, 탐색만 찾은 예시가 5개다(p=0.041). 둘을 합치면 70개로 탐색 단독보다 15개 많다. 탐색이 닿지 않는 깊이인데도 절반 넘게 찾는 것은 같은 출력을 내는 더 짧은 프로그램이 있기 때문이다.
- **시간.** 탐색이 예시당 0.03~0.05초, 모델이 0.3~0.4초다(CPU 4코어).

이 표가 6.1절을 설명한다. MBPP+에서 이 연산 라이브러리로 풀리는 과제는 대부분 연산 두 개 이내이고, 그 범위는 전수 탐색이 이미 다 본다. 학습한 제안기가 값을 하는 곳은 전수 탐색이 닿지 못하는 깊이다. 깊이를 하나 늘리면 전수 탐색의 후보는 연산 수만큼 곱으로 늘지만 모델의 비용은 프로그램 길이에 비례할 뿐이다. 다만 이것은 합성 프로그램에서 잰 것이다. 실제 과제에서 세 단계짜리 프로그램이 얼마나 필요한지는 재지 않았다.

## 7. 한계와 키우려면

- **자연어를 모른다.** 과제 설명은 "어떤 연산의 이름이 나왔는가"라는 목록으로만 들어간다. 그 목록은 규칙 엔진의 키워드 표가 만든다.
- **연산 라이브러리 밖으로 나가지 못한다.** 출력은 교사가 만든 연산 328개의 조합뿐이다. 반복문이나 조건문이 필요한 과제는 풀 수 없다.
- **실제 과제에서 전수 탐색을 넘지 못했다.** 모델이 유리한 것은 합성 프로그램의 세 단계짜리에서만 확인했다(6.3절).
- **학습 분포가 합성이다.** 무작위 프로그램과 무작위 입력으로 배웠다. 사람이 내는 과제의 분포와 다르다.
- **한 번씩만 돌렸다.** 모든 실험이 시드 하나다. 3절의 비교는 학습률을 조정하지 않았고, 5절의 평가는 150개씩, 6.3절은 100개씩이다.
- **합성 데이터가 실행마다 조금 달랐다.** `most_common` 연산이 문자열 동점을 프로세스마다 다르게 처리했다. 같은 시드로 만든 평가 세트를 두 프로세스에서 비교하니 기존 연산 세트 600개 중 1개가 달랐고, 새 연산 세트 400개는 322번째부터 달라졌다. 비율을 재는 앞쪽 150개는 같았다. 그래서 3절의 세 실행은 같은 생성기·같은 시드를 썼지만 학습 시퀀스가 글자 그대로 같지는 않다. 이 문서의 측정이 끝난 뒤 동점을 먼저 나온 값으로 정하도록 고쳤다. 고친 뒤의 재평가 결과는 [가능성 검토](rule_distillation_feasibility.md) 9절에 적었다.
- **범용 모델로 가려면** 데이터와 연산량이 여러 자릿수 더 필요하다. 현실적인 다음 단계는 두 가지다. (1) 같은 구조를 유지한 채 연산 라이브러리와 프로그램 깊이를 키운다. 6.3절대로라면 학습한 제안기가 값을 하기 시작하는 지점이다. (2) GPU가 생기면 공개 코드 말뭉치로 수천만 파라미터 모델을 학습해 자연어 설명을 직접 읽게 한다. 어느 쪽이든 제안을 실행으로 검증하는 구조는 그대로 쓴다.

학습 예산이 벽시계 시간이라 스텝 수와 최종 수치는 장비와 그때의 부하에 따라 달라진다. 학습은 다른 프로그램(llama.cpp 서버 포함)이 꺼진 상태에서 돌린다. 4코어를 나눠 쓰면 측정 시간을 비교할 수 없다. 모델 가중치(`outputs/seedlm/`)는 Git에서 제외했고, 실행 기록은 `reports/seedlm/`에 있다.
